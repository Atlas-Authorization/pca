# Production-readiness plan: everything marked experimental

Release baseline: PCA 0.4.2 plus the 0.5 additive work on this branch. Owner request: bring everything currently marked experimental to production-ready. This plan inventories it, defines "production-ready" precisely, classifies each item, and groups the closable work into build tracks.

**Method and limits.** Read-only review of the source tree, tests, READMEs and the documents named in the brief. Nothing was built or run, so test counts are line counts of test files, mutation status is inferred from the presence of `mutation-kill-*` test files (no scores were measured here), and "fail-closed on every path" is an audit task (track work), not a finding. Where a claim below is a judgement rather than evidence, it says so.

**Honesty rule used throughout.** Nothing that depends on an unperformed audit, ceremony or hardware programme is called production-ready. After the engineering work such items can honestly carry **"experimental: hardened, awaiting independent audit"** at most (the label wording is an owner decision, see O-9). Engineering work moves an item to **production** only when its definition of done (below) is met without such a dependency.

## 1. Definition of done ("production-ready")

An item may carry the `production` tier only when all eight hold. Items are scored against these as DoD-1 to DoD-8.

| # | Criterion |
|---|---|
| DoD-1 | **Fail closed.** Every error path (malformed input, missing store / revocation source / policy / key / collateral, clock problem, backend exception, absent optional dependency) denies or throws a typed error. Nothing downgrades to pass or to a weaker label. A missing required component is audited with a table of "missing X, result Y". |
| DoD-2 | **Exact-outcome tests.** Positive and negative cases assert the whole result (`toEqual` on the settled verdict / reason), not just "did not throw". Each claim has a test that fails when the check is removed (hand-applied, recorded). Adversarial inputs (truncated, oversize, duplicate keys, wrong type, replayed, expired) are covered. |
| DoD-3 | **Clean mutation gate.** The module is in the Stryker set, with no surviving mutant that is not a justified, written-down equivalent. Fresh-module tests pin constants. No timing assumptions, no child-process-only coverage. |
| DoD-4 | **Cross-language conformance where the feature is wire-level.** Vectors in the conformance corpus (layer named) and at least the TypeScript, Go, Rust and Python verifiers agree, with zero disagreements. Pure local helpers are exempt, and say so. |
| DoD-5 | **Threat model and security-contract coverage.** Each security claim maps to a T-/G- id in the threat model and an invariant in the security contract, with enforcing function, trusted inputs, state, failure behaviour and test (the traceability check passes). |
| DoD-6 | **Docs.** A reference page, a runnable quick start, failure-mode table, and a limits section, written to the public-docs rules (no repo paths, no internal names). |
| DoD-7 | **Honest assurance labels.** The verdict labels what actually held (`software` vs `hardware`, `attested_vm` vs `snark`, awaiting-audit crypto), `unsupported` is reported, and README, manifest and `maturity.json` agree. |
| DoD-8 | **No placeholder stubs in the shipped path.** No in-memory-only default for a security state, placeholder JSON-LD context, "reference" backend, mock backend or stale header comment in published `dist`. Test doubles live behind `/testing`. |

Cryptographic items need one more gate that engineering cannot supply: **DoD-X, independent review** (audit of the construction and implementation). It is the dividing line for classification (b).

## 2. Classification scheme and totals

- **(c)** recommend cutting or deprecating (move to a clearly separate research namespace, or unpublish), with the reason.

## 3. Feature groups inside `@atlasauth/pca`

Evidence base for all groups: `maturity.json` lists 74 experimental modules, about 38,000 lines of source. Nearly every module has a unit test file and most have one or more `mutation-kill-*` files (round 12 to 14 fresh-module tests exist for most intent, attestation and ledger modules). The Core entry point still reaches 24 of these modules at run time (the `core_experimental_baseline`: intent-v2, intent-binding, semantic-threshold, attestation, ledger, beacons, oracle-facts, param-provenance and others), so any defect here is a defect on the Core path. That coupling is breaking item B8; the additive way to start is the `ext/*` subpaths (Track 3).

### 3.1 frost (6 modules): FROST, PedPoP DKG, networked FROST, FROST + PQ co-signature, PQ threshold

1. **What / who.** Threshold Schnorr signing over Ed25519 (RFC 9591), a DKG with proofs of possession, a blame round and an echo round, a networked round-1/round-2 coordinator, and a hybrid where a post-quantum ML-DSA co-signature rides along. Users: guardian or custodian deployments that want one signature out of `t` of `n` shares held in separate trust domains. The default step-up (independent-share multisig, production) already serves everyone else.
2. **State (evidence).**
   - `frost.ts` is vector-exact to RFC 9591. Nonces are one-shot (`frostSign` refuses reuse and zeroizes in place; zero nonces refused). Randomness is `H3(random(32) ‖ secret)`.
   - The header and trust model say plainly: not hardened against side channels (BigInt scalar arithmetic is not constant-time); no official DKG test vectors exist (RFC 9591 is signing-only), so the DKG is validated by round-trip only; the DKG assumes an authenticated broadcast channel and private point-to-point channels the module does not provide.
   - `frost-net.ts` runs both parties in one process by default (its header says one host compromise holds every share). Hosted guardian "FROST" holds all shares on one server, so it adds no custody separation.
   - Tests: `frost`, `frost-dkg`, `frost-net`, `frost-pq`, `frost-dkg-canonical`, `frost-r6-alias` plus six `mutation-kill-*` files; a dudect-style timing harness runs FROST signing with positive and negative controls. Conformance: `frost-pq-vectors.json` only; there is no cross-language FROST verifier corpus and no native FROST implementation (TypeScript only).
3. **Gaps against DoD.** DoD-1: DKG channel failures depend on the caller. DoD-4: no native cross-checks of the aggregate signature path (Ed25519 verification is standard, so verification already works everywhere; signing and DKG are TypeScript-only, which is acceptable if stated). DoD-5: no security-contract entry for FROST. DoD-7: results carry `awaiting_audit: true`; that label must stay until the audit. DoD-X: not performed.
4. **Classification: (b) for all six.** Needed: an independent cryptographic review of the signing implementation (nonce lifecycle, binding-factor computation, constant-time properties) and of the DKG design (it is a custom PedPoP variant with a justified-complaint round, with no standard behind it). Engineering that can be done first (Track 8, size L): move scalar arithmetic to a constant-time path (noble `Field` ops or the `curve25519-dalek` wasm core already built for MPC), a pluggable authenticated-channel interface with a reference mTLS implementation and fail-closed channel errors, DKG test vectors derived from an independent implementation (ZF FROST in Rust, differential), a persistence interface for round-1 nonces that survives restarts without allowing reuse (store a spent marker before signing), an audit scope document, and a security-contract entry that states the assumptions. `pq-threshold` and `frost-pq` duplicate the `@atlasauth/pca-pq-threshold` package: keep one implementation (Track 1). Label after engineering: "experimental: hardened, awaiting audit". Recommendation to integrators stays as in the trust model: the multisig default for production custody.

### 3.2 attestation (22 modules)

1. **What / who.** Verifies that a key or a model weights digest ran inside attested hardware or software: AMD SEV-SNP, Intel TDX (DCAP, PCS collateral), Azure MAA, Google Confidential Space, NVIDIA SPDM with RIM and OCSP, PUF roots, software attestors, allowlists and signed allowlist anchors, strict X.509 and validity handling, an agent passport. Users: operators of confidential-VM fleets; anyone using `agent_binding`.
2. **State (evidence).**
   - The review premise "hardware quote parsing not implemented" is stale; the gap analysis (item 5.1) records that the verifiers exist and are tested on real evidence (`*.realsilicon.test.ts`, `attest-nvidia-own-h100`, `attest-multiroot-real`). The module header of `attestation.ts` still says the opposite and ships in `dist` (S7). That is a DoD-8 defect, fix is XS.
   - Fail-closed behaviour is the strongest area: gate `required` defaults true, require-when-bound denies without attestation, nonce freshness is anchored to server issue time, the assurance report separates `software` / `hardware` / `multi_root` / `unknown`, and `requireAssurance` refuses weaker evidence. `attestation-nonce.test.ts`, `mutation-kill-attestation*.test.ts` pin this. The extension also has a formally related port in `pca-verified-core` (`ext-attest` differential tests).
   - Known open items from the traceability notes: no test simulates a compromised vendor signing key (T-028); no test for one root of several signing a forged token with a valid-looking chain (listed gap 7); vendor roots are classical, not post-quantum.
   - Hosted surface verifies software attestors only; hardware verification runs in the resource server.
3. **Classification, split.**
   - **(a), 8 modules** (`attestation`, `attest-allowlist`, `attest-allowlist-anchor`, `attest-pq-software`, `attest-proved`, `x509-strict`, `x509-validity`, `passport`): software-mode logic, allowlisting and PKI parsing contain no vendor or hardware dependency. Work (Track 4, size L): replace the stale header; the forged-root test (T-028 / gap 7); an exhaustive fail-closed table (missing collateral, clock skew, expired nonce, unknown algorithm, trailing DER bytes) with exact outcomes; DER/X.509 differential tests against OpenSSL and a second parser on a corpus including malformed and non-minimal encodings; conformance vectors for the allowlist anchor (wire-level: signed tree-head plus inclusion proof) in at least TypeScript, Go and Rust; a security-contract entry for attestation and the assurance report; docs rewritten without repo paths (S12). After this the software-mode path can be labelled production. Passport is now signed (issuer signature, validity window, subject key binding, distinct reason codes, hardware evidence verified through the attestation verifiers), has a consumer (the optional `requirePassport` in `authorize()`), vectors and a reference page; DoD-3 (Stryker: no surviving mutant in `passport.ts` or the authorize passport branch), DoD-4 (TypeScript, Go, Rust and Python agree on `passport-vectors.json`) and DoD-5 (security-contract invariant C-12) are now met as well.
   - **(b), 13 modules** (all vendor verifiers: `attest-amd-snp`, `hardware-sevsnp`, `attest-intel-dcap`, `attest-intel-tdx`, `attest-intel-collateral`, `attest-azure-maa`, `attest-maa-keys`, `attest-maa-pins` and its data, `attest-gcp-confidential-space`, `attest-nvidia-spdm`, `attest-nvidia-rim`, `attest-nvidia-ocsp`). Blocked on: (1) an independent review of the quote and certificate parsing and the chain logic (these parse attacker-supplied binary structures); (2) ongoing access to real hardware and vendor collateral: a live canary that fetches current PCS / KDS / MAA / RIM / OCSP collateral and verifies fresh quotes from at least one SNP, one TDX and one H100 machine on a schedule, and handles TCB recovery and certificate rotation; (3) the vendor roots are a fixed trust assumption. Engineering that can be done first (Track 4): a scheduled real-evidence canary job (the owner supplies the machines, see O-3), collateral-expiry alarms, a parser fuzz corpus per quote format, a pinned-root rotation procedure, and TCB-status policy tests (out-of-date, revoked, SW hardening needed). Label after engineering: "experimental: hardened, awaiting audit"; honest claim "verifies quotes from the listed vendors against pinned roots; unaudited".
   - **(c), 1 module** (`attest-puf`, 765 lines): physical unclonable function roots need PUF hardware and a helper-data service that no listed consumer uses (no import outside tests). Move to the research namespace or remove; revisit only with a named hardware partner.

### 3.3 zk-compliance (1 module, `zk.ts`, 1,100 lines)

1. **What / who.** Lets a resource server accept "this action satisfied the policy" without seeing the plan or policy. Three backends: a Groth16 compliance circuit (BN254), a Policy-VM SNARK (BN254 or BLS12-381), and the attested-VM mode (a prover VM signs a statement). Users: regulated or confidential-policy deployments.
2. **State (evidence).** A carried `zk_compliance` with no hook fails (never ignored). Labels `groth16`, `policyvm_snark` (only when pinned to action, policy and plan), `attested_vm`. `circuits/setup.sh` and `policyvm.setup.sh` generate a **throwaway local powers-of-tau and a single contribution** (comments say a fresh run yields an equivalent setup). The circuits cover a quantized subset, not the full predicate language, custom caveats or chain signatures; the Policy-VM circuit takes risk inputs from the prover; its commitments are SHA-256 over a fixed layout, not canonical JSON. The 6-to-1 binding multiplicity change needs a new setup ("not done"). Tests: `zk`, `zk-bls12381`, `zk-canonical`, `zk-binding-tag`, `zk-policyvm-pinning`, `mutation-kill-r13-g1-zk-*` (fake snarkjs).
3. **Classification: (b) for the SNARK backends.** Needs: a real multi-party Phase 2 ceremony per circuit (and a public Phase 1 reuse of a widely contributed ptau with its hash pinned), plus an independent circuit audit (under-constrained signals are the classic failure). Engineering first (Track 8, size L): ceremony tooling and a verifier of the transcript; circuit constraint tests (every public signal changed, every witness signal perturbed, must fail); remove the prover-supplied risk inputs by binding them in the statement or labelling them; a circuit-versioning scheme so a re-setup is a new vk id, never an in-place change; cross-language verification of the same proof (Rust verifier via `arkworks`) as a conformance layer; an honest `ceremony: single-party` marker in the assurance report until a real ceremony exists. **Attested-VM mode is (a)** (Track 4, size M): it is honest as a mode; to be production it needs the prover key bound to a hardware attestation of the VM measurement (link `attest-proved`), prover-key rotation and revocation, statement freshness and replay tests, and docs stating it is a trusted signer and not a proof. Label after engineering: attested-VM "production, with the trust statement"; SNARK "experimental: hardened, awaiting ceremony and audit".

### 3.4 optimistic (2 modules: `optimistic`, `bond-settlement`)

1. **What / who.** Optimistic execution: an agent claims compliance, a challenge window opens, a recomputable fraud proof slashes a bond. Users: payment and high-throughput deployments that cannot afford synchronous full checks.
2. **State.** Solid and well tested (`optimistic.test`, `bond-settlement.test`, `bond-settlement.hardening.test`, `mutation-kill-bond-settlement`). Every settlement transition is guardian-signed; a slash needs the ledger to re-verify the fraud proof or a post-claim revocation. Library balances are in memory. Hosted balances are internal accounting with no payment rail. Effects are not rolled back (application's job). A plain `bond_ref` reports `bond: not-enforced` in Core. No conformance vectors (it is not a Core wire feature, it is an extension member).
3. **Classification: (a), size L (Track 3).** Work: a `BondStore` interface with atomic transitions, a conformance suite for stores (as `pca-store-conformance` does for replay), a reference durable store and a crash-recovery test (crash between "claim open" and "slash"); every transition's idempotence under retry with exact outcome assertions; a challenge-window clock that cannot be moved by the claimant; fail-closed when the bond store or the guardian key is absent; wire vectors for claim, fraud proof and settlement record in the conformance corpus (at least TypeScript and Rust verifying); security-contract entry; docs that state "internal accounting only; no money moves". Label after: production for the ledgered protocol; real-money settlement is explicitly outside the claim.

4. **Status (0.5, Track 3).** Built, all additive: `BondStore` contract with atomic compare-and-swap transitions (`commitBondPlan`), the conformance suite in `pca-store-conformance` (22 checks, five defective stores it flags), `KvBondStore` over any `DurableKv` as the reference durable store, `StoreBondLedger` with typed fail-closed errors and no in-memory default, idempotence of every transition under retry with exact outcomes, a challenge-window clock the claimant cannot move (ledger-stamped `registeredAt`, `max(clock, store high-water)`, 30 s floor, claim digest bound), crash-recovery tests between claim open and slash (in process and by `SIGKILL` at both durable-state commit points), wire vectors for claim, window, fraud proof (structural) and settlement record verified in TypeScript, Go, Python and Rust (zero disagreement), security-contract entry C-13, the guide "Optimistic claims and bond settlement" ("internal accounting only; no money moves"). **Label: hardened, not production.** Open against DoD: DoD-8 (the in-memory `BondLedger` still exists with an in-memory default; removal is the breaking item B17), DoD-X (no independent audit), and DoD-3 until the mutation record below is clean. The shared fraud-proof vectors are structural; the Policy-VM recomputation that convicts stays TypeScript-only.

### 3.5 intent (24 modules)

1. **What / who.** Binds a signed intent (and its fidelity and residual risk) to the action, with committed intent maps, session accumulators and monitors, classifier-derived and oracle-fact dimensions, signed action schemas, offer sets, parameter provenance, label receipts, objective risk, proof-of-progress and revocation of intents. Users: any deployment that wants "what was the agent trying to do" enforced, and the hosted `pca-intent` routes (route tests exist).
2. **State.** This is the most conformance-covered experimental area: intent binding has normative rules in the conformance README (rules 12, 16 to 19), generators (`gen-conformance-intent*.mjs`) and policy-layer vectors. Almost every module has a `mutation-kill-r13/r14-*-fresh` test. Open issues: the Core path imports 24 experimental modules; the classifier and semantic judgement are signed verdicts, so quality of judgement is not verified, only its signature and freshness; `action-schema.ts` has the highest density of "unsupported / stub / not implemented" markers (16) and needs review for importer stubs; semantic distance is a plan-graph proxy.
3. **Classification: (a), size XL (Track 3).** Work: (i) audit each of the 24 modules for DoD-1 with a "missing X gives Y" table (no session store, no oracle, expired fact, unknown dimension, unknown schema version); (ii) review `action-schema.ts` markers and delete or finish every importer that is a stub; (iii) extend conformance to the remaining non-corpus members (history window, accumulators, sequencer receipts) and run them in Go, Rust and Python; (iv) `ext/intent` subpath and a lazy-hook seam so Core stops loading it (the additive half of B8; the break itself is an owner decision, O-7); (v) mutation gate on the modules not yet in the set (`progress`, `intent-acc`, `objective-risk` are large: 1,184, 610 and 748 lines); (vi) honest docs: the layer proves binding and bounds, not that the classifier is right. Label after: production for binding and enforcement; classifier and oracle outputs documented as signed assertions by their issuers.
4. **Status (0.5, Track 3 intent half): DONE for binding and enforcement; frontier modules stay experimental.** (i) the DoD-1 audit is `intent-dod1-audit*.test.ts` and the failure table of the intent layer page (100+ rows; fixed: `verifyIntentRequired` clock coercion, `objectiveRisk` on a missing taint or age, opt-in `requireAttestedState`); (ii) `action-schema.ts` has no unsupported or stub marker left; the importers were finished (OpenAPI parameters, local references, composition, `+json`), and the reserved members are documented as unread; (iii) `intent-state-vectors.json`, 3,045 cases for accumulators, history windows and monitors, and sequencer receipts and key sets, with zero disagreement in TypeScript, Go, Rust and Python; (iv) `ext/intent` and the `extensions` seam already shipped with B8, the Core baseline is empty and stays so; (v) the Stryker set already contained every intent module; the run over all 24 is recorded in the track report, with the equivalence ledger updated; (vi) the intent layer page, threat model T-053 to T-057, guarantees G-20 and G-21, contract C-15 to C-19, maturity map split into `intent` (hardened; production needs a clean Stryker run over all 24 modules) and `intent-frontier` (experimental). Open: the optional anchoring (`verifyIntentAnchor`) rests on the ledger feature and the attested classifier gate on the attestation feature, and the in-process session store is volatile (B16 makes durable the default).

### 3.6 ledger (2 modules: `ledger`, `beacons`)

1. **What / who.** Per-principal append-only Merkle log with signed tree heads, witness cosignatures and equivocation detection; dead-man liveness beacons and a global kill switch. Users: auditors and operators who need tamper evidence and a stop button; Core reaches both.
2. **State.** Well covered (`ledger`, `ledger.hardening`, `ledger-witness-scope`, three `mutation-kill-ledger*`, `beacons`, `mutation-kill-beacons`); fuzzing found and fixed non-throwing violations earlier (audit-in-tests). `verifyWitnessedHead` and `detectEquivocation` exist; no independent witnesses are operated (T-040), so a malicious operator can still present split views; censorship is undetectable.
3. **Classification: (a), size M (Track 3), plus owner action O-5.** Work: Merkle proof vectors (inclusion, consistency, tree-head signature) in the conformance corpus across languages; a durable `LedgerStore` interface with conformance suite; beacon clock-skew and replay tests with exact outcomes; consistency-proof verification at checkpoint boundaries; docs for operating a witness (a reference witness service in a minimal container). Production claim: tamper evidence **given at least one honest independent witness**. The witnesses themselves are operator/owner work.

4. **Status (0.5, Track 3).** Built, all additive: `LedgerStore` contract (compare-and-swap appends and checkpoints), conformance suite (17 checks, six defective stores it flags), `KvLedgerStore` reference, `StoredLedger` (verifies every stored checkpoint on open: signature, `prev_root` chain, RFC 9162 proof at each boundary, entries reproduce each root; refuses rollback, tamper, forged and inconsistent checkpoints; `checkpoint()` verifies before signing), `verifyCheckpointChain`, `detectTreeHeadEquivocation`, Merkle and tree-head vectors in the extension layer verified in TypeScript, Go, Python and Rust, beacon clock-skew and replay tests with exact outcomes plus `createBeaconAcceptor` for durable replay protection, and the reference witness service in a distroless container (built and run on the box: unprivileged, read-only root filesystem, state on a volume, cosign round trip, restart persistence) with the guide "Operate a ledger witness". Security-contract entry C-14. **Label: hardened, not production**: the production claim is tamper evidence given at least one honest independent witness, and no independent witness is operated (O-5); DoD-X (no independent audit).

## 8. What this plan does not claim

- It does not claim any (b) item will pass an audit; audits find defects (the project's own self-audit found real ones, see `audit-in-tests.md`).
- It does not measure current mutation scores or run any suite; per-module "clean gate" is an acceptance criterion for each track.
- Sizes are estimates for agent-driven builds with the box available, excluding calendar time for external parties (audit slots, ceremony coordination, hardware procurement), which can dominate.
- "Production" for the standards bridges means correct against a named revision of a moving specification; it does not mean the specification will not change.
