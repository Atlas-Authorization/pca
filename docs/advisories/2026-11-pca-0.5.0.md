# Security advisory: two defects in PCA 0.5.0

Published with PCA 0.5.1. PCA 0.5.0 was never published to any registry or GitHub release; these defects were in the unpublished 0.5.0 code and were fixed before the first 0.5 release. Affected, if you built from the unpublished 0.5.0 code: 0.5.0 of `@atlasauth/pca` and the packages named in issue 2, and the PHP, Python and Ruby SDKs (issue 4). Fixed in: 0.5.1. Every other package and SDK in the family is republished at 0.5.1; only the PHP, Python and Ruby SDKs carry a code change beyond the packages named here (issue 4). If you run 0.5.0, upgrade to 0.5.1.

## Summary

| # | Component | Issue | Severity |
|---|-----------|-------|----------|
| 1 | `@atlasauth/pca`, `@atlasauth/pca-payments` (TypeScript) | A non-finite clock or budget stamp meant "no time passed", so a depleted-by-time budget stayed full and a charge was admitted | Medium to high |
| 2 | Reference packages (TypeScript) | Non-finite clock, skew or amount inputs were admitted by about 30 comparisons | Medium |
| 3 | `@atlasauth/pca` (TypeScript) | The NVIDIA OCSP verifier accepted a DER-malleated copy of an authentic response | Low |
| 4 | PHP, Python and Ruby SDKs | A clock or revision that is not a finite number was read as 0 or skipped: revocations dropped, plan approval expiry passed, a pinned last revision skipped | Medium to high |

We have not seen either used against a deployment.

## 1. Budget decay with a non-finite clock (fail open)

The trust budget leaks over time. The leak function computed the elapsed time only when both the decision clock and the budget's last-update stamp were finite numbers, and otherwise treated the elapsed time as zero. A NaN or infinite (plus or minus) clock, or a budget whose stamp was NaN with no issue time to fall back on, therefore kept the full budget instead of the decayed one. In `authorizeChargeCore` a charge could be admitted automatically when the decision time (`asOf`) was NaN and the budget carried no issue time. Reaching this needs the host to pass a non-finite clock or to hold a corrupted budget record; it needs no key and no forged evidence.

Fix: when either value is not a finite number the budget is treated as depleted, so the action needs a human step-up. Finite inputs behave as before.

Workaround on 0.5.0: refuse any request whose clock is not a finite number before it reaches the budget code, and validate stored budgets on load.

## 2. Non-finite clock, skew or amount inputs (fail open)

Across the reference packages, many refusals were written as a comparison that is false for NaN (for example `now > expiry` to refuse). A caller-supplied clock, skew, timestamp, budget, amount, limit, ttl, quota or depth that was NaN therefore passed expiry, not-before, freshness, window, replay-hold and cap checks. Reaching this needs the host to pass a non-finite value; it needs no key.

Fix: each refusal is now the negation of its positive condition, so a non-finite input is refused. Finite inputs behave as before. Affected: `@atlasauth/pca`, `pca-acp`, `pca-agentcard`, `pca-ap2`, `pca-attest-eat`, `pca-ciba`, `pca-dpop`, `pca-explain`, `pca-gnap`, `pca-goal`, `pca-grants`, `pca-intent`, `pca-payments`, `pca-sdjwt`, `pca-signals`, `pca-store-conformance`, `pca-vc` and `pca-webbotauth` (all under `@atlasauth/`). The native SDKs are not affected.

Workaround on 0.5.0: refuse non-finite clocks, skews and amounts before calling the packages.

## 3. NVIDIA OCSP: DER malleability

When a response was signed by a delegated responder, the verifier rebuilt the embedded responder certificate from its parsed form before checking it. Re-encoding normalised a malformed certificate (for example one with a flipped length byte) into the genuine one, so a tampered copy of an authentic response was accepted. This is malleability acceptance only: the signature, the issuer binding and the certificate contents are those of the authentic response, and no forged response or forged status is accepted. The same change makes `ocspRequest` refuse an unsupported CertID hash instead of emitting an empty algorithm OID.

Fix: the certificates are read from the response's own bytes and the strict DER parser refuses a malformed copy. A response whose certificate encoding does not match is refused with `embedded certificates do not match the response encoding`.

Workaround on 0.5.0: none needed for safety; treat the response as you would have treated the authentic one.

## 4. Non-finite clock or revision read as zero (PHP, Python and Ruby SDKs)

Three places read a value that is not a finite number as if it carried no information, and the result was admission:

- The lease registry (PHP, Python, Ruby) prunes revocations once `revoked_at` plus the TTL ceiling is past. With a NaN or infinite clock reading every comparison was false, so every stored revocation was dropped and the leases they covered read as live again. Fix: a non-finite clock prunes nothing.
- The plan registry (PHP, Python, Ruby) checks the principal's approval expiry against the clock. In PHP the clock was cast to an integer, and NaN or infinity cast to 0, which is before every expiry; in Python and Ruby a clock of negative infinity passed the expiry comparison. Fix: a non-finite clock never passes the expiry (PHP refuses the call, Python and Ruby report the plan as not executable).
- The policy-bundle verifier (PHP) skipped its rollback check when the pinned last revision was not a finite number. Fix: such a last revision is refused as a rollback.

Reaching these needs the host to supply a non-finite clock reading or a corrupted pinned state; it needs no key. The Go, Java, Kotlin, .NET, Rust and Swift SDKs use integer clocks and are not affected. The 0.6 line has further sites in modules that 0.5.x does not ship.

Workaround on 0.5.0: refuse any non-finite clock reading before it reaches the registries, and validate pinned bundle state on load.

## Upgrading

Upgrade every `@atlasauth/pca*` package, `create-pca-app` and the Python and Rust packages to 0.5.1; they are versioned in lockstep. The PHP, Python and Ruby SDKs are affected by issue 4 only; the other native SDKs are affected by none.
