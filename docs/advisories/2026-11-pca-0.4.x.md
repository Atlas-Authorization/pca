# Security advisory: fail-open verifier defects in PCA 0.4.x

Published with PCA 0.5.0. Affected: every release up to and including 0.4.3. Fixed in: 0.5.0. There is no 0.4.4; upgrade to 0.5.0.

PCA 0.4.3 stated that no forged evidence was accepted. That statement was wrong for the first three issues below, and this advisory supersedes it. Each issue is a case where a verifier accepted input it should have refused. None needs a stolen key. Whether you are exposed depends on which verifier you call and who controls its input, as described per issue.

Severities are our assessment of the worst realistic case. We have not seen any of these used against a deployment.

## Affected versions

All versions up to and including 0.4.3 of the packages and SDKs named in each issue. Versions from 0.5.0 are not affected. The native SDKs at 0.4.3 shipped only the core verifier, so issues 1 to 3 and 7 to 9 do not apply to them (they had no ledger, attestation or satellite modules).

## 1. Ledger consistency proofs (TypeScript)

Default-mode consistency verification decoded the old root and the path nodes at any length. Only the opt-in strict mode demanded 32-byte values. With an old tree size that is a power of two (for example 1), a 31- or 33-byte old root combined with a crafted new root verified as consistent. Anything relying on the append-only guarantee (head advance, witness and mesh checks) could be fooled by a proof built that way.

Fix: every mode now requires 32-byte nodes. Workaround on 0.4.x: refuse any consistency proof whose old root, new root or path entries do not decode to exactly 32 bytes, before calling the verifier.

## 2. Intel DCAP / TDX collateral (TypeScript)

The signature over `tcbInfo` and `enclaveIdentity` covers the first such member in the document, but the body that was then used came from a normal JSON parse of the whole document, where the last duplicate wins. Collateral with a duplicate member could therefore make an out-of-date or revoked platform read as up to date.

Fix: the body is read from the signed bytes. Workaround: fetch collateral only straight from Intel's provisioning service over TLS and never accept collateral from the party being attested; or reject any collateral document with a repeated top-level member before verification.

## 3. Google Confidential Space (TypeScript)

A token whose key set carried RSA `n`/`e` or EC `x`/`y` values next to a genuine, public certificate chain was verified with the key built from those values, while the chain was only checked separately to the configured root. If the key set source is attacker-influenced this allows a forged attestation.

Fix: the verification key must be the certificate chain's leaf key. Workaround: take the key set only from a source you trust, and reject any key entry whose `n`/`e` or `x`/`y` differs from its first certificate's public key.

## 4. `budget_alloc` monotonicity (all native SDKs)

The reference implementation requires that a child capability never allocates more of a budget than its parent. The native verifiers only checked that each limit was not negative, so a chain where a child carried a larger allocation than its parent passed chain verification. Budgets are usually also metered by the server, which limits the impact.

Fix: a widening chain now fails the chain check. Workaround: meter budgets server-side and treat the carried allocation as advisory.

## 5. `zk_compliance` (all native SDKs)

A PCActn carrying a `zk_compliance` member was accepted by the core verifier and the signature-only guards even when no zero-knowledge verifier was configured to check it. A carried but unchecked proof is no worse than no proof, unless your policy relies on its presence.

Fix: such a PCActn now fails the core verifier and the signature-only guards unless a verifier enforced it. Workaround: reject PCActns that carry `zk_compliance` before calling the verifier, or use the full authorize path with a zk verifier configured.

## 6. Python core verifier (Python SDK)

If an exception was raised after every core check had passed, the verifier recorded a reason but left `allow` true. The TypeScript reference reports the fault as `malformed`, which fails. We did not construct a trigger, but hostile input reaching later decision code is the plausible route.

Fix: such a fault now denies, with a `malformed PCActn` reason. Workaround: deny whenever the verdict carries a non-empty reason, whatever `allow` says.

## 7. `verifyIntentRequired` clock (TypeScript)

When the caller omitted the clock argument the expiry check was skipped. Fix: the clock is required, and a variant that takes an explicit time was added. Workaround: always pass the current time.

## 8. Accumulator declarations (TypeScript)

A host-built accumulator declaration with an unknown aggregate was read as `distinct` in the pre-state and returned an undefined result. Signed declarations were already validated on the wire, so only host-built ones were affected. Fix: an unknown aggregate is refused.

## 9. Satellite TypeScript packages

- `@atlasauth/pca-revoke`: a revocation with a non-finite `notBefore` was read as not yet in effect, so it never took effect. It is now refused when written and read, and a fail-closed check form was added.
- `@atlasauth/pca-ap2`: a mandate usage context with a NaN, negative or fractional counter made the cap comparisons pass. It is now refused.
- `@atlasauth/pca-webbotauth`: the `nbf` and `exp` of a key in a key directory were ignored. They are now enforced.
- `@atlasauth/pca-connectors`: a URL variable such as `{shop}` could contain characters that moved the request, and so the authorization code, to another host. A variable must now be a single DNS label.
- `@atlasauth/pca-explain`: a truthy but non-true `allow` was explained as an allow, and an allow contradicted by a failing check was explained as one. Both are now explained as denials.

## 10. Server-side PQ pins and classical grants (TypeScript)

`verifyPCActn`, `requirePCA` and `authorize` accept `pqPins`, a map from a grant issuer to the post-quantum public key the server pins for it, so that someone who recovers the issuer's Ed25519 key cannot mint grants. The `pq_pin` check only looked at post-quantum and hybrid grants: a classical (Ed25519) grant naming a pinned issuer passed, so the pin protected nothing against that attacker, who simply signs a classical grant. The pin is keyed by the Ed25519 issuer identity, which a hybrid issuer shares with its classical grants. Where the server resolves the grant from its own store the attacker cannot place a grant there; the exposure is where the grant comes with the presenter (an A2A task without a stored grant) or the operator relies on the pin as the control. `pq_pin` shipped in 0.4.2 and 0.4.3, so both are affected. Both layers were affected: the full verifier (`verifyPCActn`, `requirePCA`, `authorize`, and `@atlasauth/pca-a2a`, which hands its `pqPins` option to it) and the core verifier `verifyPCActnCore`, whose `pqPins` option (used with `grantFromArtifact`) constrained only post-quantum roots. The Go SDK shipped the same pass-through in 0.4.2 and 0.4.3: `VerifyOptions.PQPins` on its core verifier let a classical grant from a pinned issuer pass. The other eight native SDKs (.NET, Python, PHP, Ruby, Java, Kotlin, Swift, Rust) had no issuer-level `pq_pin` check in 0.4.x, only pins for post-quantum root keys, and are not affected. Both now refuse a classical grant whose issuer has a pin (`pq_pin: the grant issuer is pinned to a post-quantum key; a classical grant is refused`); an issuer with no pin is unchanged. An operator who wants classical grants from an issuer must not pin it.

## What to do

Upgrade every affected package and SDK to 0.5.0. Read the migration guide first: 0.5.0 also flips several defaults to safe values (see the release notes), and some integrations need small changes.

If you cannot upgrade immediately, apply the workarounds above. They reduce exposure but do not replace the fix.

## Reporting

Report suspected vulnerabilities privately to the maintainers through the security contact in the repository's security policy.
