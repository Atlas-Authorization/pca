# Changelog

All notable changes to the `@atlasauth/pca*` packages and `create-pca-app`. Every package in the family is versioned in lockstep, so a release bumps all of them together. While the version is 0.x, minor releases may contain breaking changes.

## Unreleased (0.4.2)

### Security

- **Hosted intent sessions accepted a post-quantum session root or session grant signed under a key of the caller's choosing.** `POST /v1/pca/intent/sessions` and `POST /v1/pca/intent/sessions/:sid/grants` took the signer's post-quantum key from the session root's own `principals[].pq_pk`, which is part of the submitted document. A pure ML-DSA (or other pure-PQ) signature needs no Ed25519 secret, so anyone could name an enrolled principal, list a key they generated, and have the root or grant stored; a stored grant then authorises reservations and settlements. Both routes now take the signer's post-quantum key only from the instance's PQ pin registry (`POST /v1/pca/pq-pins`); with no pin, or a pin that differs, the request is refused (400). Ed25519 roots and grants are unchanged.
- **The intent sequencer could admit past an accumulator cap (over-admission under concurrency).** The hosted sequencer (`POST /v1/pca/intent/sessions/:sid/reserve`) read the clock BEFORE taking the (session, accumulator) lock, and the window function `inWindow` excluded every event stamped after the candidate's time (`t_i > t`). A reservation committed by a concurrent request while this one waited carried a later time, so it was visible but not counted: 8 concurrent reservations of 30000 against a 100000 cap admitted 4 (120000); with times in reverse lock order, or sequencer nodes with skewed clocks, every reservation saw a pre-state of 0. Fixed on both sides: the sequencer reads its admission time and computes the reservation expiry under the lock, and an accumulator now counts every live event stamped after `t`. The spec's E_ψ uses `t_i ∈ win(t) ∪ (t, ∞)` (Intent Layer v2 §2.1 and the T11 proof note), so a reservation is never invisible to the cap, whatever the clock order; in a history whose times never decrease nothing changes. `accPreState` also throws instead of silently dropping a counted event (or a candidate) whose time is not a safe integer. Hosts that run their own accumulator store get the fix through `accPreState` / `admitIntentAction`. Verifiers are unaffected: rule 15 checks the claim against the injected pre-state and no verifier evaluates windows over a history, so there is no wire or conformance change. The same check-then-write pattern was fixed in the hosted question mailbox (a pending cap that concurrent enqueues could overshoot: 10 against a cap of 3 created 8), in step-up cosign merging (concurrent cosigns could lose a share), and in hosted payment mandates (a charge stamped ahead by a skewed node now still counts toward the `rate` caveat). Regression tests: `packages/pca/src/intent-history-window.test.ts` (deterministic, no database) plus deterministic lock-order, clock-skew and concurrency tests against Postgres.
- **Native resource-server middleware echoed attacker-controlled text into `WWW-Authenticate`.** The Python, Go, Rust, Java, .NET, Ruby and PHP guards put the denial reason (and, in some, a parse error or the presented `grant_ref`) in the challenge's `error_description`; a CR/LF in it reached the header in Python, Ruby and the Java `PcaResult` value (a header-injection vector), and made PHP's PSR-7 `withHeader` throw. Every native challenge now carries only the realm (plus the audience in Python) and the static error code, as the TypeScript `requirePCA` does; the reason stays in the JSON body. In the same pass: a non-string `grant_ref` never reaches the host's grant resolver (Python, Ruby: 401 `invalid_pcactn`), a throwing resolver fails closed instead of escaping as a 500 (Python, Ruby, .NET, PHP: 403), and the Java and .NET body carriers reject invalid UTF-8 instead of replacing it with U+FFFD. The TypeScript reference was not affected.
- **The zkVM release-gate guest enforces root caveats.** The 0.4.1 fix (caveats on the root grant outside the envelope are evaluated; `max_spend`; unknown root caveat types fail closed) is now in the RISC Zero guest too, together with the Intent Layer `intent` binding (a present signed `intent` must open the root grant's goal commitment; its fidelity and residual-risk claims are committed to the journal and checked against the relying party's policy by `pca-zkvm-verify`) and the Intent Layer v2 checks (rules 13-19, including the committed-map check whose disclosure stays private to the proof) under every signature suite but LESS: a receipt from guest version 8 (image id `0c97a02b9d6f99131fb1d76207377ccb3546be8b8f6c33387ab078b1d49453a7`) proves that the root grant's own caveats held and that any intent claim is bound to the grant. The previous guest (`3b1eebb5...`, version 7) is superseded: `pca-zkvm-verify` refuses its image id and its journals. The guest also takes a pure-PQ or hybrid session root's PQ key only from the verifier's pin (`intent_v2.session.pq_pins`, bound into the journal through `context.intent_v2.ctx_digest`), as the TypeScript reference and the native verifiers now do: the released guest is version 9 (image id `c5107456f3885cfe87f0da62d24aa273e1fe94c982eed57324374dcefa80ac39`), and version 8 (`0c97a02b...`), which accepted the key named in the root's own `principals[]`, is superseded too (`MIN_GUEST_VERSION` 9). See `sdks/zkvm-pca/CHANGELOG.md`.
- **PHP verifier (`php-pca`): a non-string caveat `type` could satisfy a caveat.** `Pca::evaluateCaveats` matched the caveat `type` with a loose `switch`, so a caveat such as `{"type": true, "at": <future>}` was evaluated as `expires` (`true == 'expires'`) and could be satisfied. Like the TypeScript reference (strict `===`), a non-string `type` is now unsatisfied. 0.4.1 is affected; regression in `tests/CaveatTypeStrictTest.php`.

### Breaking

- **Post-quantum and hybrid session roots need a verifier-side pin.** `verifySessionRoot(S, { pqPins })` verifies a non-Ed25519 root only under `pqPins[S.signer]` (your own enrolled-key registry, or `pqPinFor` over a signed binding); with no pin it fails closed (`... needs the signer's PQ key pinned by the verifier (pq_pins) ...`), and a pin that differs from the root's `pq_pk` fails. The signer's own `principals[].pq_pk` is no longer a trust anchor; when present it must agree with the pin. Ed25519 roots verify exactly as before (pins are not consulted). The `intent_session` and `accumulators` checks read the pins from the new verifier context member `intentV2.session.pq_pins` (`{ [ed25519 key]: pq_pk }`; any other value is a malformed context). On the hosted API, pure-PQ and hybrid session roots and session grants need the signer's key registered first with `POST /v1/pca/pq-pins`. The conformance corpus pins this on every verifier (`session-root-*-unpinned`, `-pin-mismatch`, `-pin-other-signer`, `-principal-entry-mismatch`, `ctx-session-pq-pins-*`).

### Fixed

- **Evidence bundles for post-quantum or hybrid sessions never verified.** `verifyEvidenceBundle` checked the session root, G_0, the delta grants and each PCActn without any PQ pin, so a PQ session failed even when the reader pinned the principal's key. It now takes the keys from `trust.principals[].pq_pk` (the reader's out-of-band pins, never the bundle) for all of those checks. A PQ bundle whose principal is pinned without a PQ key, or pinned with a different key, is refused.
- **The transparency-anchored allowlist could hang on a large feed.** `verifyAllowlistAnchored` ran its conflict and highest-version scan over the whole feed in quadratic time, which stalled for a long time near the feed size limit. The scan now runs on a linear-time witness subset that gives the same answer.
- **The durable allowlist failed on stores that answer without running the update callback.** `verifyAllowlistDurable` reported `malformed` when a `DurableKv.update()` returned the stored record without calling the updater. That record is now judged as the value at update time through the same rollback checks; a missing or corrupt record still fails closed as a rollback.
- **`agent_binding.min_measurement` with an SVN bound failed open or parsed loosely.** `{svn: "5"}` (or a NaN / infinite / fractional / negative bound, an object without `svn`, `null`, a number) used to enforce nothing; it now fails closed (`min_measurement is malformed ...`) and makes `requiresAttestation` true. The measured `runtime_measurement` must be the canonical decimal text of a safe integer: `"0x10"`, `"1e1"`, `" 8 "`, `"08"` are no longer read as SVNs 16, 10, 8. Same rule in `passport.matchesBinding`. Proved in `Attest.dfy` (`MinBad`, `MalformedMinFailsClosed`).
- **`verifyPCActn` refused every grant with a pure post-quantum or hybrid root signature**, even when the core verifier accepted it: the policy layer (`decide()`) re-verified the chain without the verifier's stored grant or PQ pins. `decide()` now receives the same authority as the core verifier (`DecideInput.trustedRoot`, the stored grant, plus the server-side `pqPins`); `deriveDecideInput` sets `trustedRoot` to the stored grant and takes optional `pqPins`. Fail-closed is unchanged: without that authority a PQ root is still refused, and a pin that disagrees still refuses. When both the stored grant and a pin for the root issuer are given, they must agree: `verifyChain` (`ChainPolicy.trustedRoot` with `pqPins`) and `decide()` refuse a root whose `pq_pk` differs from the pin even if it is byte-identical to the stored grant; the stored grant never overrides a disagreeing pin. The same rule now holds in the standalone chain API of all nine native verifiers (Go, Python, Rust, Java, Kotlin, .NET, PHP, Ruby, Swift), which had the same override; new `chain_pin` vectors `chainpin-*-trusted-root-*-pin` (31 in all).

### Changed

- **More of the verifier now runs machine-proved code.** The information-flow taint computation and its gate, Merkle inclusion verification, the attestation decisions (agent binding, multi-root, the attestation verifier and hook, the durable and transparency-anchored allowlist) and the threshold / admission / release kernels of `decide()` now run the Dafny-proved implementations from `@atlasauth/pca-verified-core`. No API change. The strict-JSON / canonical encoder, the regex engine, the predicate and caveat evaluator, strict Merkle consistency and revocation membership, and the attestation nonce store have proved implementations that are opt-in via the environment variable `PCA_VERIFIED_CORE` (`1` for all, or a comma list of `wire`, `regex`, `policyvm`, `merkle-strict`, `noncestore`), because they are slower or stricter.

### Added

- **Intent Layer v2, wire batch W-B (conformance rules 16-18).** Grants can now constrain facts about the world, the optimality of a choice, where each parameter's value came from, and labels from attested classifiers, all computed by the verifier and never taken from the agent:
  - `decideIntentWorld` (rule 16) fills `env.world` from signed oracle facts (`pca-fact`, keys pinned per world, freshness bound, at least `min_oracles >= 2f+1` fresh facts from distinct oracles, lower median; string facts must agree), from fixed relational functions (`sub`, `ratio_ppm`), and from a site-signed offer set (`pca-offer-set`): `excess` = chosen price minus the cheapest offer that satisfies the intent filter, with a coverage check that refuses a search narrowed beyond the filter and a completeness requirement.
  - `decideParamProvenance` (rule 17) classifies each material or critical parameter from the refs declared in `intent_session.prov` against the server's trusted-input registry (the agent can only raise a label), resolves label receipt refs (`pca-labels`, bound to the session and to the value's digest), enforces flow rules for the data classes they carry, and turns tainted values into a question (tap or typed) or a deny (`critical_max`, `material_tainted`, `critical_tainted`).
  - `decideClassifierDimensions` (rule 18) accepts classifier verdicts (`pca-intent-classification`) only from allowlisted keys, bound to the session and the content digest, with pinned measurements, combined k-of-n; the label is `env.class.<id>`.
  - `decideReadPurpose` (read-side purpose limitation with field minimisation), `flowAllowed`, and `decideIntentWB`, which runs rules 16-18 in order for a verifier pipeline.
  - `@atlasauth/pca-intent`: layered intent (`decideLayers`, `latticeView`, quorum-signed shared-layer approvals `verifyQuorumApprovals`; a ceiling is never a question), Ω̃ dimensions for world, provenance and classifier values, within-grant regret accounting, calibrated confusion matrices with Clopper-Pearson bounds folded into the residual risk (`classifierAwareResidualRisk`, the `γ_max` JIT gate), and frames (`checkFrame`: write sets, `env.pre` / `env.post` postconditions, exact deltas; an unattributed out-of-frame change vetoes the cell).
  - New conformance primitives `intent_world`, `intent_provenance` and `intent_classifier` (`gen-conformance-intent-wb.mjs`); the rules are in `packages/pca/conformance/README.md`.
- **Intent Layer M2 (conformance rule 12): the signed `intent` member.** The optional PCActn member `intent` `{ref, map_digest, goal_salt, fidelity_ppm, residual_risk_ppm}` and the `intent` check bind the action to the IntentStatement and Intent Map the root grant's goal commits to; verifier policy `intent: {require, min_fidelity_ppm, max_residual_risk_ppm}`, fail closed. No member and no policy leave the verdict unchanged. Suite-agile `signIntentStatement` / `verifyIntentStatement`, `intentRef`, `intentMapDigest`, `signIntentMapAttestation`, `signIntentObservation` and their verifiers. Conformance vectors `intent-*` (`gen-conformance-intent.mjs`).
- **Intent Layer v2, wire batch W-A (conformance rules 13-15): signed action schemas, sessions, delta grants, trajectory caps, intent revocation.**
  - Sites publish a signed action schema (`/.well-known/pca-actions.json`, `pca-action-schema` v1; `signActionSchema`, `verifyActionSchema`, `actionSchemaDigest`; MCP and OpenAPI draft importers). The new `schema` check maps every action to the schema's outcome space or to the fail-closed cell: an undeclared verb or parameter, a missing required parameter, or a value outside its declared domain is a terminal deny, never a question (`conformAction`). The wallet floor keeps money, party, contact, person, credential and message parameters at least material. Discovery documents gain an `intent` block.
  - The PCActn gains the optional signed member `intent_session` (`session`, `root`, `seq`, `schema`, accumulator claims, and the W-B commitments). The `intent_session` check binds the action to a principal-signed session root (`pca-intent-session`), to the session grant it is rooted at (G_0 or a delta D_k, minted only by a principal key, chained by `seq` / `prev`), and, when the session names a revocation source, to a fresh signed epoch proving the session, map, delta and profile ids are not revoked (bounded exposure window).
  - The `accumulators` check recomputes per-session totals (sum, count, distinct, max over task, sliding or periodic windows, optionally keyed) and monitor states from verifier-held state or a sequencer-signed reservation receipt; the agent's claimed post value must match, and grant predicates read `env.acc.<id>.post` / `env.mon.<id>.state`, so splitting a purchase cannot evade a cap. `MemoryIntentSessionStore` / `admitIntentAction` serialise admissions per session.
  - `intent_required` / `intent-denied` / `schema-violation` / `ceiling` problem responses with a site-signed `pca-intent-required` body; `env.canon.<name>` projections for boolean, set and array parameters; the CAEP `intent-revoked` event in `@atlasauth/pca-signals`.
  - `@atlasauth/pca-intent`: Ω from the schema (`deriveOmegaFromSchema`), trajectory dimensions and lift (`augmentOmega`, `liftAction`), the monotone accumulator prior, lazy elicitation and delta minting (`decideVisit`, `mintDelta`), and owner-signed append-only intent profiles (`signIntentProfile`, standing deny / permit layers, veto import, `profileUsable`). Intent Maps record the v2 learner settings (monotone prior, asymmetric noise, population prior) so they replay.
  - Atlas API: `/v1/pca/intent/schemas`, `/sessions` (roots, grant chain, sequencer reserve / settle under a row lock, questions / clarify mount points, revocation and signed epochs) and `/profiles`; migration 0152 (hand-applied).
  - New conformance vectors `schema-*`, `session-*`, `acc-*`, `layers-*` and primitives `intent_schema`, `intent_revocation` (`gen-conformance-intent-v2.mjs`).
  - A sequenced accumulator names its sequencer by a long-lived ROOT key; receipts name the signing key by `kid` in a root-signed key set (`pca-sequencer-keys`, `verifyReceiptAgainstHolder`), so a rotated signing key never ends a session. Atlas publishes its set at `GET /v1/pca/intent/sequencer-keys` and signs session revocation epochs with the same root.
  - Numeric dimensions are statistics over cells in closed form, so a declared domain of any size (up to 2^53 - 1) costs O(cuts), with no per-value tables.
  - `pca schema init|sign|verify|conform|publish` in `@atlasauth/pca-cli`; `draftActionSchemaFromMcp`, `applySchemaDecisions` and `conformToolCall` in `@atlasauth/pca-mcp`.

## 0.4.1 - 2026-10-12

Security release. Lockstep: every `@atlasauth/pca*` package and `create-pca-app` 0.4.1, the Python `atlas-pca` and its seven framework adapters 0.4.1, and the `atlas-pca`, `stark-pca` and `pca-folding-ivc` crates 0.4.1; the native verifiers (Go, Java, Kotlin, .NET, PHP, Ruby, Swift) carry the same fixes. The npm packages pin their internal dependencies exactly, so every package is republished to pull in the fixed `@atlasauth/pca` core. 0.4.0 is deprecated (npm) and yanked (PyPI, crates.io): upgrade to 0.4.1 or later.

### Breaking

- **Unknown root caveat types fail closed.** Caveats on the root grant (other than its first `envelope` caveat) are now evaluated, and a caveat type the evaluator does not implement is unsatisfied, so the action is denied (`policy` check, reason `root caveat(s) not satisfied: <types>`). Grants that carry free-form data as a root caveat (for example a `note`) are denied from 0.4.1: move that data out of the caveat list or into a known caveat type.
- **The `PCA-Action` header must be strict unpadded base64url** of UTF-8 (padding, the standard alphabet and whitespace are refused with 401); see Fixed below.

### Security

- **Caveats on the root grant outside the envelope were not enforced.** The policy layer (`decide`, `verifyPCActn`, `requirePCA`) evaluated the caveats inside the grant's `envelope` caveat and the caveats delegation hops appended, but caveats the principal placed directly on the root grant (next to the envelope) were signed and then ignored. A grant carrying, for example, a root `max_spend` or `expires` caveat got no enforcement of it. Root caveats are now evaluated exactly like delegated caveats (attenuation applies from the root): every caveat on the grant except its first `envelope` caveat must hold, and a type the evaluator does not implement is unsatisfied (fail closed). A failure denies through the `policy` check with the reason `root caveat(s) not satisfied: <types>`. If you deploy grants that carry root caveats the evaluator does not know (for example a free-form `note`), those grants are now denied: move such data out of the caveat list or into a known type. New `rootCaveats(grant)` and `policyCaveats(grant, chain)` helpers. The Dafny model of the policy decision (`PolicyVm.dfy`) gains `RootCaveats`, `RootCaveatsEnforced` and `RootMaxSpendEnforced` (re-proved, 288 verified).
- **New `max_spend` caveat type** `{ type: 'max_spend', usd }`: satisfied when the action's parameters carry an `amount` that is a number from 0 to `usd` inclusive and, if a `currency` is given, it is exactly `"usd"` or `"USD"`; a missing or non-numeric amount does not satisfy it. Introspection reports it as `remainingBudgetHints.maxSpendUsd` and `envelopePermits` honours it when params are given.

### Fixed

- **Pure post-quantum threshold shares can be carried in a PCActn.** The `wire` check required every `threshold.shares[i].sig` to be 64 bytes, so an ML-DSA-65 share (3,309 bytes) verified through `verifyThreshold` but could never travel in `threshold`. Share `alg`, `sig` and `pq_sig` are now validated per suite, like the leaf (`validateShareSignatureWire`): an unknown or non-string `alg`, a length that does not match the suite, or a missing or stray `pq_sig` fails `wire`. A share's `pq_pk` echo stays a threshold-check rule.
- **The `PCA-Action` header is decoded strictly.** `defaultExtract` (and so `requirePCA` and the framework adapters that re-export it) and `decodePcaHeader` used lenient decoders that accepted padding, the standard base64 alphabet, surrounding or embedded whitespace and invalid characters. The value must now be strict unpadded base64url of valid UTF-8 text, the same rule as every other byte field; anything else is refused (`PcaHeaderError`, a 401 from `requirePCA`). `@atlasauth/pca-mcp-rs` uses the same decoder.

### Conformance

- 20 `r041-share-*` vectors (394 core vectors in all), `primitives.caveat_eval` (41 entries: root `max_spend` exceeded is DENIED, within the limit ALLOWED, plus the baseline caveat types, root/hop ordering and the envelope exclusion) and `primitives.pca_header` (27 entries). New generator stage `gen-conformance-041.mjs`. The adversarial set is unchanged.
- Docs: the wire-format reference and the conformance README now describe wire version 2 exactly (actn/v2, `pq_sig` unsigned, eleven hop members, role-bound agent share, per-suite share lengths, root caveat evaluation, strict header).

### Not yet covered

- The zkVM release-gate guest still mirrors the 0.4.0 decision (no root caveats, no `max_spend`); see the TODO in `sdks/zkvm-pca/README.md`.

## 0.4.0 - 2026-10-11

Lockstep release of the whole family (`@atlasauth/pca*` and `create-pca-app` 0.4.0; the Python `atlas-pca` and its seven framework adapters 0.4.0; the `atlas-pca`, `stark-pca` and `pca-folding-ivc` crates 0.4.0). 0.3.x is superseded. This release closes red-team rounds 4, 5 and 6 (core, API, aliasing/encoding, zkVM and native verifiers) and the hardening program that followed: the Dafny-proved decision core is now called from production (`@atlasauth/pca-verified-core` 0.4.0, first release), durable-state lock recovery is fenced and model-checked, the hosted API does no signature or post-quantum work before a request is matched to a stored grant and is rate-limited per source, network and instance, and every native verifier enforces the root PQ pin, the caveat caps and the 512 KiB document cap with shared conformance vectors. The detailed entries below are grouped by finding.

### Breaking changes (summary)

- **`deriveDecideInput` requires `ctx.grant`.** It no longer falls back to the presented chain's root; a missing grant throws `DecideInputGrantRequired` (`code: 'grant_required'`).
- **`frostAggregate` requires `verificationShares`** and verifies every share (canonical scalar and the RFC 9591 share equation) before aggregating; calling it without them throws (R6-ALIAS-07). `frostCosign` and the network coordinator already passed them.
- **`@atlasauth/pca-a2a`, `@atlasauth/pca-ap2` and `@atlasauth/pca-payments` decide against the server-held grant or mandate.** `verifyA2ATask` / `verifyA2APaymentMandate` / `pcaA2AMiddleware` need `grant` or `expectedRootIssuer` (`A2AAuthorityError`); `verifyPcaBinding` needs `mandate` (and `recentChargeTimes` when the mandate limits the charge count); `authorizeCharge` / `chargeDecideInput` need the verified grant (`MandateGrantError`). The hosted `POST /v1/pca/payment-mandates/authorize` keeps the spend ledger server-side and requires an `idempotency_key`.
- **`decide()` no longer guesses the plan node.** The node is only the one named by `nodeId` (on the server path the signed `pcactn.plan.node_id`); without it the semantic distance is the worst case and the reversibility class is the action's own, else unknown (`reversibility_max` refuses). Callers that relied on matching the action's verb and resource must pass `nodeId`.
- **Durable-state format (one-way).** Journal records and heads carry the writer's lock generation, and recovery writes append-only fence files (`state.fence.<gen>-<random>`). Older versions cannot open a directory written by 0.4.0 (they fail closed); 0.4.0 reads directories written by older versions.
- **zkVM guest image `3b1eebb5...fdad`.** The `zkvm-pca` guest image id changes from `e922536c...91a8` to `3b1eebb56b046e737fb15009bdd065b67d7938cb8d47f3f3f0dadc801f84fdad` and the journal gains a first field `guest_version` (7). Pin the new id; receipts from older images are refused as `Superseded` by `verify_with_context`.
- **Regex work budget.** Each decision document gets one regex budget (64 evaluations, 8,192 source characters, 5,000,000 worst-case steps) shared by every `re:` resource and `matches` condition in the envelope and its caveats, plus a per-request budget on the hosted API. A constitution or contract is evaluated as one document. Once exceeded, further evaluations fail closed, and a refused evaluation counts as "matched" in a prohibition trigger. Ordinary policies never approach the budget.
- **Threshold shares: a share that names a `pq_pk` must name exactly its role's registered key** (every suite, TypeScript and all nine native verifiers). A different key (even with signatures valid under the registered key), a non-string value, or a `pq_pk` on a share for a role that registers none is refused with `share for role <r> names a pq_pk that is not the key its role registers` (verified core: `Threshold.dfy` `PqPkMismatch`). Four new shared conformance vectors.
- **`TRUSTED_PROXY_COUNT` (hosted API).** The client address used for rate limits, quotas and audit is derived only from `TRUSTED_PROXY_COUNT` trusted proxies (default `0`: the socket address, `X-Forwarded-For` ignored) and the header chosen by `TRUSTED_PROXY_HEADER`; a forwarding chain shorter than the count falls back to the socket address. Set it to your real proxy count (behind one load balancer: `1`).
- Also breaking, detailed below: the hosted default suite list is Ed25519 plus the Ed25519 hybrids (`pca.allowedSuites` to accept pure PQ); native standalone chain APIs need `pq_pins` / `trusted_root` for non-Ed25519 roots (R4-01); `create-pca-app` `express-rs` loads the grant from its own store; `memoryNonceStore` refuses when full; `/actions/dry-run` returns `401` for an expired or wrong-audience PCActn; `@atlasauth/pca-mpc` wire version 2.

### Fixed: templates authorize with the full verifier (R6-CORE-04); AST trusted-root scanners (R6-CORE-05)

- **`create-pca-app` templates enforce the grant's scope (R6-CORE-04).** The `express-rs` guard verified with `verifyPCActnCore`, which evaluates no predicate, limit or caveat: with its own refund-only grant it returned 200 for `stripe.delete_customer` and `github.delete_repo`. It now guards with `requirePCA` (grant from the server's store, `allowedSuites` Ed25519, server clock, revocation hook, replay counter and trust budget, the principal-authorized plan root, `DEFAULT_REQUIRED_CHECKS`); authentication failures are 401, authorization denials 403. `node-quickstart` uses `verifyPCActn` and shows an out-of-scope denial. Every template depends on `@atlasauth/*` `^0.4.0`. The `agent-facade` example, the `pca-revoke` README (the registry is the revocation hook of `verifyPCActn`) and the native `python-pca` / `swift-pca` READMEs no longer present a structural verify as the authorization decision.
- **`requirePCA` gains `allowedSuites` and `pqPins`; `verifyPCActn` gains `pqPins`.** With `pqPins`, a non-Ed25519 grant must carry a `pq_pk` equal to the pin for its issuer, else the new `pq_pin` check fails (401). `allowedSuites` is snapshotted with the rest of the configuration.
- **BREAKING: `deriveDecideInput` requires `ctx.grant`.** It used to fall back to the presented chain's root, so the Policy VM could evaluate an attacker-minted root's predicates. A missing grant now throws `DecideInputGrantRequired` (`code: 'grant_required'`).
- **`scripts/check-unsafe-trusted-root.mjs` and `scripts/check-pq-pinning.mjs` run on the TypeScript AST (R6-CORE-05).** Shared analysis (`scripts/lib/pca-ast-scan.mjs`) with intra-file data flow: variables, destructuring, any chain index and array method, for-of and callbacks, values returned from or passed into local functions, spreads, `Object.assign`, member assignments, `Object.defineProperty` / `Reflect.set`, constant-folded computed keys, getters, case-insensitive request headers (`req.get`, `header()`, `headers[...]`, body, query). Comments and strings are never read as code. `grantFromArtifact` must be literally `true` in the same options. `.vue` / `.svelte` / `.astro` / `.html` scripts and Markdown fences are parsed. ### Fixed: durable-state operator recovery of a PAUSED holder (R6-CORE-01), liveness by PID namespace (R6-CORE-02), wedged lock shapes (R6-CORE-03)

- **Recovery is safe against a paused (not dead) holder by construction (R6-CORE-01).** Before, a holder released by `recoverDurableState` while SIGSTOPped / `docker pause`d could resume and overwrite the newer holder's commit (final state the stale value, `verify()` passing) or write a stale `state.head` that made every later open fail. The R5-F1 claim "a late-resuming old holder fails with `lock-lost` and writes nothing" was true only for a holder paused before its pre-rename lock check. Now: (1) the lock is re-checked before the journal rename AND before every head rename (and before quarantine); (2) every journal record and the head carry the writer's lock generation `gen` (inside the record hash / head MAC); (3) recovery takes the lock itself (`state.lock.<g+1>` held, `recovering: g`), records the cut in the new `state.fence` (journal tail seq and record hash; records after it need generation > g), then frees the lock (`state.lock.<g+2>`); (4) on load a record from a fenced generation after the cut, a journal that no longer holds the cut record or no longer reaches it, a generation that decreases along the chain, or a tail older than the generation that wrote the head is refused (`corrupt` / `rollback`, fail closed); a stale late head is recognised and repaired. The re-check-to-rename window cannot be closed with rename(2); what slips through it is refused on load, never silently accepted. Cost of that case: the newer holder's records after the recovery are no longer on disk and the store fails closed until `recoverFromCorruption: true` (which now also re-fences: generation >= the quarantining holder from genesis). Model-checked in `formal/tla/DurableFence.tla` (passes; removing the fence, the head repair, the lock-first recovery order or the cut pin each yields a counterexample).
- **Format (one-way):** records and heads written now carry `gen`; journals/heads without it are read as generation 0 and keep working. An older version cannot open a directory written by this one (hash mismatch, fails closed).
- **Recovery that itself crashes midway (R6-CORE-01 follow-up).** A `recoverDurableState` killed after taking `state.lock.<g+1>` but before its fence landed left a lock naming a dead process; a same-namespace waiter took it over like any dead holder and wrote no fence, so the paused holder of `g` could still rename its journal late over the waiter's commits and be loaded (found by the extended `DurableFence.tla`, case `df_bad_takeover_nofence`). Now a waiter that takes over a dead lock marked `recovering` carries the mark into its own lock and cuts + fences under its own generation before it loads (a taker killed before its fence lands passes the duty on, `df_bad_no_inherit`); a waiter in another namespace still times out and the operator re-runs recovery. The recovery lock also records `start` and `boot` so a reused pid cannot make the dead recovery look alive. **Fences are append-only**: `state.fence` used to be one list rewritten whole (read, add, rename), so a fence writer paused between its read and its rename (a taker superseded by a second recovery) dropped every fence written meanwhile, and a later cut could then pin a record that the dropped fence refused (found by TLC, `df_rcrash_both_3c_2rec`; kept as the negative case `df_bad_fence_rmw`). Each fence is now its own immutable file `state.fence.<gen>-<random>`; the `state.fence` list is still read (older versions) and holds the genesis fence that `recoverFromCorruption` writes, which also moves old fence files aside. A directory with per-file fences cannot be opened by an older version. Model: a crash after every recovery step, safety (`Safe`) and liveness (`NoWedge`, `AckedOrFailedClosed`) for both the takeover and the re-run path. Tests SIGKILL a real recovery process at each of its seven steps (test-only hook `PCA_DURABLE_TEST_RECOVER_CRASH_AT`, honoured only with `NODE_ENV=test`) with the holder paused in each of three places. The README now states the threat model: `state.fence` / `state.lock.N` are unsigned on purpose, and automatic takeover never breaks a lock held under another hostname or PID namespace.
- **Liveness by PID namespace (R6-CORE-02).** Recovery's "never release a live holder" check now runs whenever the recorded PID namespace equals ours, whatever the recorded hostname (UTS namespace, `--pid=host`, renamed host); hostname is used only when the record has no namespace.
- **Every wedged shape has an operator path (R6-CORE-03).** A legacy single-file `state.lock` is released with `recoverDurableState({ dir, force: true, legacyLock: true, expectedHolder })` (moved aside to `state.lock.legacy-recovered-*`, kept); readable but incomplete top records (`{}`, `[]`, `{"st":"held"}`, string pid, missing/empty nonce, missing host) are released with `expectedHolder: 'unreadable'` (copied fields are refused for them, as `'unreadable'` is for complete records). `lock-timeout` names the real blocker (the legacy file instead of a non-existent `state.lock.0`) and the call to use.

### Hardened: hierarchical pre-auth limiting (closes the saturated-bucket cycling residual of R6-API-05)

- **Public PCA routes are limited per source, per network and globally.** Each pre-auth request is charged to its source bucket, then to its network bucket (IPv4 /24, IPv6 /48; new quota `publicPerNetworkPerMin`, default 8x `publicRateLimitPerMin`) and to one global pre-auth bucket per instance (new quota `publicPreAuthGlobalPerMin`, default 64x). A source that is already limited is refused before it charges the aggregates. The `429` message names the level (source, network or instance).
- **`InMemoryRateLimitStore` never evicts a live limited bucket.** Saturated windows keep their queue position (the order they became saturated, i.e. expiry order); only expired ones are reclaimed. When the store is full of live limited buckets, new keys share one overflow bucket (`overflowHits`) instead of evicting anyone.
- Measured: a spray of 100,000 IPv4 addresses over ~391 /24s admitted exactly what was left of the global allowance (3,835 of 100,000: 3,840 minus the victim's own 5) and could not reset a limited victim; 100,000 IPv6 /64s inside one /48 admitted exactly the network allowance (40). A 100k-key spray in which every key saturated its own bucket left a limited victim limited. Before: the old store evicted the victim and gave 1,000 of 1,000 new keys their own bucket.

### Fixed: API findings R6-API-01..05 and the still-open R5-API-03, -05/06, -07

- **No signature verification before the root matches a stored grant (R6-API-01).** `POST /v1/pca/actions` and `/actions/dry-run` no longer call `verifyChainCheap` (it ran one Ed25519 verify per hop plus the leaf before the lookup, 53-76% of a full verify). The order is now: size caps, structural parse, `aud`/`iat`/`exp`, `grant_ref == cap_chain[0].id`, suite allowlist and `holder_pq` commitments, stored-grant lookup and root equality by `capHash`, the strict v2 wire form, the per-source PQ budget, then signatures (leaf first, then the chain under the stored grant). Measured on a 65 KB 8-hop hybrid chain through the HTTP route against Postgres: the anonymous path went from 108 ms of incremental cost (full verify 142 ms, ratio 0.76) to 0.66 ms (full verify 88 ms, ratio 0.0075); the test asserts < 10%. Behaviour change: a forged leaf or broken chain is now refused after one grant lookup instead of before it, and junk naming an unknown grant gets `unknown_grant` rather than a signature verdict. `verifyChainCheap` stays exported but is no longer used by the API.

- **In-memory rate-limit store (R6-API-05).** `InMemoryRateLimitStore` (also the Redis fallback) evicts in O(1): windows sit in two LRU queues, unsaturated and saturated, and a new key evicts an expired saturated window, else the least-recently-used unsaturated one, and a saturated one only when every bucket is saturated. A victim at its limit is no longer reset by a distinct-key spray, and a full 50k-key store no longer rescans every window per insert (per-insert cost ratio 50k:1k keys went from 37x to flat). Failure and nonce maps evict their oldest entry in O(1).
- **Regex caches (R5-API-05/06).** The two 512-entry caches that were cleared wholesale when full are replaced by one bounded LRU (`regex-cache.ts`; exports `regexCacheHas`, `regexCacheStats`, `setRegexCacheSourceProvider`, `REGEX_CACHE_*`) keyed by SHA-256 of the pattern, with per-source admission (64 of 512 entries per source; `RegexBudget.request(source)` carries the source), a total-weight cap and no clear on any path.
- **Stored non-array `pca.allowedSuites` fails closed (R5-API-07).** The config reader now returns `[]` (refused with a typed `500`) for any present but malformed value (a bare string, `null`, a number, an object, a list with a non-string/empty/over-long entry, more than 16 entries); before, a non-array was read as "unset" and widened to the default suites, and a partly invalid list was silently narrowed.
- **Mesh consistency docs.** `POST /v1/pca/mesh/ledger/consistency` documents that a size-0 `old_root` is the RFC 9162 empty-tree root (SHA-256 of the empty string), not `''`.

### Security: R4-01, the root PQ pin reaches the nine native verifiers and the artifact-rooted TS callers (BREAKING)

### Breaking: `@atlasauth/pca/durable-state` lock protocol replaced; the `staleLockMs` option is removed

The file store's lock used to be a single `state.lock` that any process could break once it was older than `staleLockMs`. That was unsound (model-checked in `formal/tla/DurableLock.tla`, reproduced on the real code): an owner stalled past the threshold had its lock given away and then overwrote the newer commit, so a consume-once update could be told "first" twice, and concurrent breakers could displace a fresh lock. The lock is now a set of immutable numbered files `state.lock.<g>` created with `link(2)`; a live holder is never superseded and a lock is taken over only from a provably dead holder on the same host (`docs/pca/security/replay-store-verification.md`).

- **Removed:** `DurableStateOptions.staleLockMs`. Delete it from callers; nothing replaces it (age never breaks a lock).
- **Behaviour change:** a holder that is alive but stalled now BLOCKS other processes until it dies; they fail with `lock-timeout` after `lockTimeoutMs` instead of robbing it. Restart or kill a wedged holder.
- **New:** `DurableStateError` codes `lock-lost` (the generation is no longer ours just before a commit; cannot occur under the protocol, fails closed) and `link-unsupported` (the state directory's filesystem lacks working hard links with exclusive-create semantics; thrown by `openDurableState`, never opens a store whose lock could not be exclusive).
- **Requirements, now enforced or documented:** one host only; a local filesystem with working `link(2)` (not NFS/SMB/FUSE; some overlay mounts).
- **Mid-upgrade safety:** a legacy single-file `state.lock` is still honoured as a holder (waited for unless its owner is provably dead, never deleted or renamed), so an old process still running on the host cannot be raced by a new one. Do not run old and new versions on one directory over time; the legacy handling is a safety net for the upgrade window, not a supported mode.

### Security: Swift verifier accepted mixed-order Ed25519 public keys; weak-key conformance family `ed`

The TypeScript reference (`keys.ts`) is stricter than plain RFC 8032: besides S < L and canonical encodings it rejects every small-order and every mixed-order (A + T, T of order 2, 4 or 8) public key and R. A verifier on a plain library accepts a mixed-order key whenever the signature hash k is 0 (mod 8). Auditing all nine native verifiers: Go, Python, Ruby, PHP, .NET, Rust, Java and Kotlin already rejected every such artifact (own subgroup arithmetic, `verify_strict` plus explicit checks, or libsodium/BouncyCastle subgroup validation). The Swift verifier checked only a small-order table before CryptoKit, so a mixed-order leaf, hop or threshold-share key with k = 0 (mod 8) VERIFIED. Fixed: `Ed25519Torsion.isPrimeOrder` (exact `[L]P = O`, fixed-width field arithmetic, cached per key) is now required for the public key; R needs no separate test because CryptoKit's cofactorless equation then only accepts a torsion-free R (pinned by the mixed-order-R vectors). New deterministic family `adv-ed-*` (133 vectors: leaf, delegation hop and root hop, each with mixed-order A for T of order 8/8/4/2 with k = 0 mod 8, mixed-order R, all eight small-order keys with R = identity and S = 0, six non-canonical small-order encodings, all eight small-order R plus non-canonical ones, small-order A and R together, and S + L) and 44 `ed-weak-*` agent threshold shares in `primitives.threshold_share`. Every vector is verified by the generator to be accepted by a plain RFC 8032 equation (cofactorless or cofactored) and is rejected by the reference.

### Breaking: shared 512 KiB cap on the raw size of a PCActn document, and the caveat caps now on all nine verifiers

A PCActn JSON document larger than 524,288 bytes (512 KiB, measured in UTF-8 bytes of the raw text) is now refused as a `wire` failure, with the reason `artifact exceeds size limit (max 524288 bytes)`. The check is the FIRST thing every verifier does, before any parsing, so a 760 KB or 1 MiB document costs one length comparison (O(1) for byte strings; a single byte count for text). Documents above 512 KiB that verified before (the strict JSON profile's own bound is still 1 MiB, now unreachable for a PCActn) no longer do. The cap leaves room for a hybrid LESS PCActn (about 130 KB of base64url `pq_pk` plus the signature, roughly 200 KB in all). Deployments that wrap PCActns in larger envelopes are unaffected; only the PCActn text itself is bounded. Constants: `MAX_ARTIFACT_BYTES`, `ARTIFACT_SIZE_REASON` and `artifactTooLarge` (`@atlasauth/pca` `pcactn.ts`, checked in `decodePCActn`); every native verifier carries the same names in its own convention and checks in its raw-text entry point (Go `ParsePCActn`, Python `verify_pcactn_core` and the server header path, PHP `Pca::verifyJson`, .NET `Pca.VerifyRaw`, Rust `verify_pcactn_json_policy` and the middleware header path, Java/Kotlin `verifyPcactnJson`, Ruby `verify_pcactn`, Swift `PCA.verify(json:)`). The header paths of the PHP, .NET and Rust middleware check the decoded length before parsing as well.

The shared caveat caps (256 per hop, 1,024 per chain, reason `chain exceeds caveat limit (max 256 per hop, 1024 per chain)`) now exist in the Go, Python, PHP, .NET, Rust and Swift verifiers too, in the same position as in the TypeScript reference, Ruby, Java and Kotlin: after the 16-hop bound, on raw list sizes, before any hashing or signature work. All nine native verifiers and the TypeScript reference now agree on every over-cap vector.

Conformance: new `size` family in the full adversarial set (`adv-size-*`: limit-1, limit, limit+1, multi-byte widths at and over the limit by bytes but under it by characters, and a realistic ~200 KB hybrid-LESS-sized PCActn that must be accepted); these 200 to 600 KB documents are in `vectors-adversarial.json.gz` and the all-languages gate only, never in the vendored core. `limits` in the vector files gains `max_artifact_bytes`, `max_caveats_per_hop` and `max_caveats_per_chain`. In the gate's size/time corpus (`tools/pca-diff-fuzz/gen/dos.mjs`) the exact-boundary size vectors move from 2^20 to 524,288 bytes, the 1 MiB bombs that used to reach the parser are now refused by the cap (a `-under-cap` twin of each stays just below 512 KiB so the strict parser is still exercised), `wide-keys-40k-distinct` is now `wide-keys-25k-distinct` (the 40k-key object is 600 KB and is expected to reject as `wide-keys-40k-distinct-over-cap`), and `artifact-size-*` vectors cover limit-1, limit, limit+1 and the LESS-sized document. `atten-15000-caveats-prefix-compare` and `chain-17-hops-fat-caveats` (both about 760 KB) are now rejected immediately by the size rule in every language. The Dafny model is unchanged: `Wire.dfy` models the strict JSON profile's own 1 MiB input bound, and the 512 KiB artifact cap is a stricter pre-check in the trusted glue that only turns an accept into a reject.

### Breaking: shared hard caveat caps on every verifier (256 per hop, 1,024 per chain)

A capability chain is now rejected (`cap_chain` / `chain` check fails, reason `chain exceeds caveat limit (max 256 per hop, 1024 per chain)`) when ANY hop carries more than 256 caveats or the caveat counts summed over all hops exceed 1,024. Caveat lists are cumulative and append-only, so the per-hop cap bounds a hop's whole list and the chain cap bounds the total work of every attenuation prefix comparison (at most 1,024 canonical hashes, however deep the chain). The check reads raw array lengths and runs before any hashing, signature or root-equality work, after the existing 16-hop depth bound. Chains above the cap that verified before (for example a 500- or 2,000-caveat root) no longer do; the golden vectors carry at most 3 caveats per hop and the in-repo examples at most 5. Constants: `MAX_CAVEATS_PER_HOP`, `MAX_CAVEATS_PER_CHAIN`, `CAVEAT_LIMIT_REASON` (`@atlasauth/pca` `capability.ts`; Ruby, Java and Kotlin verifiers carry the same names). The check sits in the trusted glue before `decideChain`; the Dafny model abstracts caveat lists as opaque sequences, so its proofs are unchanged.

Conformance: `adv-atten-many-500` and `adv-atten-many-2000` now expect reject (and `adv-atten-many-255` accepts); `caveat-lists/root-many-identical-1000` now expects reject (`-256` accepts). New DoS vectors at limit-1, limit and limit+1 for both caps (`caveats-per-hop-*`, `caveats-per-chain-*`) in `tools/pca-diff-fuzz/gen/dos.mjs`; `atten-15000-caveats-prefix-compare` and `atten-3000-identical-caveats-quadratic` now expect reject. Ruby verifier: the strict JSON parser and canonicalizer take fast paths (plain-run strings, short integers, no-escape strings), with byte-identical output.

### Security: round 3 red-team fixes (breaking)

Summary of the review rounds: `docs/public/security-review-summary.md`.

- **R3-01 `@atlasauth/pca` (CRITICAL)**: a pure-PQ or hybrid chain ROOT was verified under the root's OWN `pq_pk`; the expected Ed25519 issuer was only string-compared, so a root grant "issued by" any principal could be forged (reproduced on `POST /v1/pca/grants`, and in the AP2, GNAP, ABE and policy-vm verifiers). Delegated hops are unchanged (bound to the parent's `holder_pq`).
  - New `pqPins` options: `verifyChain` policy, `decide` (`DecideInput`), `describeEnvelope(chain, now, root, policy)`, `MeshTrust`, `TranslateArgs`, `VerifyTranslateOptions`, `@atlasauth/pca-ap2` `verifyPcaBinding`, `@atlasauth/pca-gnap` `authorizeGnapAction` / `verifyGnapToken`, `@atlasauth/pca-abe` `CapabilityAttributeOpts`.

- **R3-06 `@atlasauth/pca` + API (Medium)**: PQ pin rollback. ### Changed (breaking)

### Breaking

- `@atlasauth/pca-gateway`: **fixed the Envoy ext_authz adapter denying every request that has a query string** (Envoy forwards the request target including `?query`, and route matching used it verbatim, so `/refunds?x=1` was an unmapped route). Added tests against the real Fetch `Request`/`Response` classes, the Worker entry running in `workerd` (Miniflare), the AWS-documented Lambda authorizer events (REST, HTTP API 1.0 and 2.0) and the Envoy ext_authz request shape (constructed, Envoy not run).
- `@atlasauth/pca-ciba`: **`auth_req_id` was derived from public step-up fields and was therefore guessable** (CIBA Core 7.3 requires at least 128 bits of entropy); the broker now issues 160 random bits. **Starting a flow twice for one step-up silently reset an approved decision to pending**; a repeated start now returns the live flow. `requested_expiry` must be a positive integer, the verb is rejected if it cannot be a single scope-token (a space used to smuggle extra scopes), and `binding_message` is sanitized to one short plain-text line. Validated with the CIBA Core 1.0 examples and the `openid-client` library end to end.
- `@atlasauth/pca-ap2`: checked against the official AP2 schemas and documentation examples (Ajv). **The mandate chain is not the SD-JWT format the current AP2 schemas define**; the README and package description no longer claim wire compatibility. x402 settlement fixed against the x402 v1 specification: `maxAmountRequired` is now in atomic units (it was the decimal amount), `X-PAYMENT` is standard base64 (it was base64url), and `error` and `maxTimeoutSeconds` are present.
- `@atlasauth/pca-attest-eat`: tests only. RFC 7515 A.3, RFC 8037 A.4, RFC 7519 6.1 and RFC 9711 Appendix A examples, plus two-way checks against `jose`. Limits found are recorded in the README (full `application/eat+jwt` typ refused; lenient base64url in the signature segment).

#### FHE risk gate and VDF timelock validation

- `@atlasauth/pca-vdf`: **fixed `vdfVerify` / `verifyTimelock` accepting `y = 0, pi = 0` (or any multiple of the modulus) for every input and step count**, which released a timelock with zero work. `y`, `pi` and `x` must now be canonical units of the group; `vdfVerifyDetailed` reports the refusal reason. **Breaking:** `setup` is renamed `insecureDevSetup` (result branded `insecureDevOnly`), and the timelock functions refuse its moduli, anything under 2048 bits and structurally weak moduli unless `allowInsecureDevModulus: true` is passed (`checkProductionModulus`). The bundled RSA-2048 modulus is now compared with the RSA Laboratories and Wikipedia published digits; prover and verifier are cross-checked with an independent Python/GMP implementation (self-written vectors, labelled as such).
- `@atlasauth/pca-fhe`: **fixed evaluation crashing on a policy whose scaled weights or kappa-weights are all zero**, and **fixed a WASM memory leak (about 80 MB per call) on malformed or truncated blobs**; blobs are now validated against the SEAL stream envelope first and all SEAL objects are released on every path. Added property-based tests against the plaintext risk gate, a two-way cross-check against TenSEAL 0.3.18 (independent SEAL build), a parameter-security assertion against the HE Standard 128-bit table, and reason-asserting tamper and wrong-key negatives.

#### Identity and transparency standards validation

- `@atlasauth/pca-scitt`: **the Merkle leaf was canonical JSON of the base64url statement, so no off-the-shelf RFC 9162 verifier could check a receipt**; leaves are now `SHA-256(0x00 || statement bytes)` and receipts carry a detached payload (RFC 9942 section 4.4). Logs and receipts from earlier builds do not verify. Added `checkStatement` (returns the failure reason), RFC 9162 consistency proofs (`TransparencyService.consistencyProof`, `verifyConsistencyProof`), and fixes to the CBOR codec (a leading U+FEFF in text was silently dropped; negative integers below -(2^53-1) were accepted; floats were reported as "non-minimal integer"). Validated with the 82 RFC 8949 Appendix A vectors, `cose-wg/Examples`, the Certificate Transparency 8-leaf tree and 196 `transparency-dev/merkle` probes, and two-way checks with pycose, cbor2 and pymerkle.
- `@atlasauth/pca-sdjwt`: **the verifier only understood flat, top-level disclosures and `present()` threw on any array-element disclosure**, so none of the SD-JWT examples in RFC 9901 could be processed. Verification now follows RFC 9901 section 7.1 (recursive `_sd` and `...`, decoys, reused digests, unreferenced and colliding disclosures, security-critical claims, default `_sd_alg`), requires a KB-JWT `iat` and `aud`, and adds `expectedKbAudience` and `kbMaxAgeSec`. All eight SD-JWTs in RFC 9901 verify under its published key; credentials and presentations interoperate with `@sd-jwt/core` 0.22.0 in both directions.
- `@atlasauth/pca-dpop`: **`verifyDpopProof` ignored `nonce` and `ath`** (they were documented but never enforced). Added `expectedNonce` and `accessToken`. The three RFC 9449 example proofs verify (and match an independent `node:crypto` signature check); PyJWT 2.10.1 interoperates in both directions.
- `@atlasauth/pca-vc`: **`_sd_alg` was emitted inside `credentialSubject` (RFC 9901 requires the top level), which `@sd-jwt/core` rejects**, and **`verifyPassportVC` did not pin the algorithm, so a raw public key could be used as an HMAC secret**. Also checks `typ`, the VC 2.0 context and type, duplicate and unexpected disclosures. `verifyRequestSignature` gained `requiredComponents`, `maxAgeSec` and an `alg` check. did:key base58btc is validated against the multiformats vectors and Python `multiformats`/`base58` (43 keys); RFC 9421 signatures interoperate with `http-message-signatures` 2.0.1.
- `@atlasauth/pca-spiffe`: **`parseX509Svid` accepted any certificate with one URI SAN, including CA certificates and certificates without `digitalSignature`**, and **`verifyJwtSvid` accepted HS256 when given raw key bytes**. Added the X509-SVID leaf rules, `verifyX509Svid` (chain, CA flags, `keyCertSign`, path length, validity, trust domain), DER-based SAN extraction and the JWT-SVID algorithm and `typ` rules. Validated with go-spiffe's character rules and X.509-SVID test certificates, py-spiffe 0.3.2, and OpenSSL and Python `cryptography` chain verdicts.
- `@atlasauth/pca-webbotauth`: added the dictionary form of `Signature-Agent` (`"signature-agent";key="..."`, as in the current draft and Cloudflare's library), `components`, and `requireExpires`; parameters are emitted in the draft's order. The draft-05 Ed25519 vectors for no `Signature-Agent` and the legacy string form are reproduced byte for byte, and RFC 9421 B.2.6 verifies. **The draft-05 vector A.2.2 is signed over the unquoted dictionary member value, contradicting RFC 9421 section 2.1.2 and its own printed signature base**; this package and `web-bot-auth` 0.2.0 reject it, and the test documents the discrepancy.
- `stark-pca` and `stark-pca-plonky3` (security): **the opaque `policy_commitment` and `action_commitment` were bound into the proof by a prefix only (128 bits in `stark-pca`, 64 bits in the Plonky3 crate)**, so a SHA-256 commitment had at best 64-bit / 32-bit collision / second-preimage strength. Both must now be exactly 64 hex digits (anything else is refused) and are bound in full: four 64-bit limbs per commitment in `stark-pca` (public inputs 16 to 24 elements), eight 32-bit limbs per commitment in the Plonky3 crate (Goldilocks is below 2^64; public values 16 to 30). Committed proof fixtures regenerated; tests flip every limb, and a regression test covers commitments differing only in the last hex digit. This is a public-input layout change: old proofs do not verify.
- `@atlasauth/pca-attest-eat`: `verifyEAT` accepts the short `typ` form `eat+jwt` as equivalent to `application/eat+jwt` (RFC 7515 4.1.9, case-insensitive); other `typ` values are still refused.
- Validation (post-quantum): `@atlasauth/pca-pq-threshold` ML-DSA-65 is tested against the official NIST ACVP FIPS 204 vectors and against dilithium-py and liboqs; `@atlasauth/pca-mpc-lwe-ot-wasm` against the official ACVP FIPS 203 ML-KEM-768 vectors and kyber-py; `@atlasauth/pca-fndsa-wasm` against an independent C implementation in both directions (no official FN-DSA vectors exist yet); `@atlasauth/pca-fndsa` integration tests now run through the real wasm backend. Note: the K-PKE key derivation in `@atlasauth/pca-mpc-lwe-ot-wasm` differs from ML-KEM key generation and is documented as such.

## 0.2.0 - 2026-10-08

> Superseded by 0.3.0. 0.2.0 shipped the defects listed under 0.3.0 Fixed (including security fixes in pca-vdf, pca-mpc-wasm, pca-oprf and the STARK crates); upgrade.

### Breaking

- **The resource-server verifier now lives in `@atlasauth/pca`.** Verdict computation and the framework-neutral `requirePCA` guard are exported from `@atlasauth/pca` itself. PCA no longer depends on any other product's SDK. The framework middleware packages (`@atlasauth/pca-fetch`, `-express`, `-fastify`, `-hono`, `-next`) depend only on `@atlasauth/pca` and no longer depend on any other product's SDK.
- **A new mandatory verification check, `grant_ref_bound`.** The holder-signed `grant_ref` of a PCActn must be a non-empty string byte-equal to the id of the root capability (`cap_chain[0].id`). The check is part of the default required checks and of the discovery defaults, and it fails closed on an empty or malformed chain. Previously a holder could sign arbitrary fresh `grant_ref` values and land on an empty replay/budget namespace for each action. PCActns that do not carry a matching `grant_ref` are now rejected; the conformance vectors were extended accordingly (the check is implemented identically in the TypeScript reference and the Go, Python, Ruby, PHP, .NET, Java, Rust, Kotlin and Swift verifiers).
- **AMD SEV-SNP: the invented "weights" slot is removed.** SEV-SNP has no native weights-measurement field; the previous convention read bytes that are actually part of the AMD report's committed-TCB / build fields. Reports no longer yield a `weights_measured` claim from those bytes. Anything that relied on that claim must obtain model-weights evidence from a source that really provides it.
- **`@atlasauth/pca-attest-eat` no longer carries its own AMD chain cryptography.** `verifySevSnpSignature` and `verifyAmdCertChain` are removed; `verifyAmdAttestation` (now async, as is `verifyFreshAttestedEAT`) delegates to the hardened `verifyGenuineSevSnpReport` in `@atlasauth/pca`. It now requires the verifier clock (`nowMs`; `verifyFreshAttestedEAT` passes its `now`), a `family` (`milan`, `genoa` or `turin`) or an explicit `trustAnchorArkSpkiSha384` in place of `rootFingerprint`, rejects debug-enabled guests unless `allowDebug` is set (replacing `requireDebugDisabled`), and enforces CA roles, strict extension parsing and the VCEK-to-report binding. `KNOWN_AMD_ARK_SPKI_SHA384` is now `{ milan, genoa, turin }`, so genuine Genoa hardware (Azure SEV-SNP) verifies.
- **The synthetic attestation profiles (SEV-SNP, Intel TDX, NVIDIA CC) are removed.** Use the real-evidence verifiers listed below.
- **NVIDIA GPU root: no workload identity by default.** The GPU root no longer derives a `runtime_measurement` from GPU state, so it composes with CPU TEE roots in an N-of-M policy instead of producing a false identity conflict. The GPU measurement digest is surfaced as `hostAsserted.gpu_measurements_sha384`; standalone deployments can supply `policy.deriveIdentity`.
- **Intel TDX: debug TDs are rejected** unless the policy explicitly sets `allowDebug`.

### Added

Attestation (verified against evidence captured from real hardware and real vendor services):

- AMD SEV-SNP report verifier with per-family ARK pins (Milan, Genoa, Turin), real report-field parsing (CPUID, committed/launch TCB, firmware versions, mitigation vectors), report v5, `minCommittedTcb` / `minLaunchTcb`, and runtime-data binding checked under AMD's signature.
- Intel TDX / DCAP quote verifier (`attestIntelDcap`) including Intel PCS collateral validation (TCB info, QE identity, CRLs), MRSEAM / MRSIGNERSEAM allowlists, and runtime-data binding checked under Intel's signature.
- NVIDIA GPU confidential-computing root (`attestNvidiaSpdm`) in the real SPDM / X.509 wire format, NVIDIA RIM golden-measurement verification and CRL revocation (`attestNvidiaRim`), OCSP revocation (`attestNvidiaOcsp`), and Hopper and Blackwell support (Blackwell RIM naming, wrong-family manifest rejection).
- Azure Attestation (MAA) root covering SEV-SNP and TDX CVMs, with a `sevSnpMinTcb` minimum reported-TCB policy and surfaced SVNs; built-in release-signed MAA trust pins (no trust-on-first-use) with multi-vantage corroboration.
- GCP Confidential Space root covering SEV-SNP and TDX on GCP.
- Multi-root N-of-M attestation policy across hardware roots, plus software/HSM post-quantum and PUF / TPM EK roots.
- Signed, versioned allowlist manifests (`attestAllowlist`), a rotation-safe MAA signing-key trust store (`attestMaaKeys`), transparency-anchored allowlist rollback protection, and crash-safe durable state (`@atlasauth/pca/durable-state`).
- `@atlasauth/pca-attest-eat`: per-session attestation freshness and channel binding emitting EAT (RFC 9711).

Authorization and protocol:

- Post-quantum t-of-n quorum certificates (`pqThreshold`): a composition of independent ML-DSA / SLH-DSA signatures with assumption diversity and rotation certificates. This is a quorum of signatures, not a compact threshold signature.
- Replay-store contract (`ReplayStore` / `CounterStore`, `guardPCActnReplay`) with a reference in-memory store, so multi-server deployments can plug in a shared store.
- Runtime-data binding for hardware attestation evidence (nonce and PCA action bound into the signed evidence).
- Step-up re-attestation: a held, attested step-up whose attestation nonce lapsed can complete with a fresh single-use nonce instead of failing unusably (hosted service).
- FN-DSA (Falcon, FIPS 206 draft) registered as the `fn-dsa-512` and `fn-dsa-1024` signature suites, backed by the new `@atlasauth/pca-fndsa-wasm`.
- LESS (a code-based signature, NIST additional-signature Round 2 candidate, not a standard) registered as the opt-in `less-cat1` and `hybrid-ed25519-less-cat1` suites (category 1, 97,484-byte public key, 1,153 to 1,329-byte signatures), usable on PCActn leaves and capability hops. Backed by the new `@atlasauth/pca-less-wasm`: the official LESS reference compiled to WebAssembly with a portable loader (Node, browsers, Deno, Bun, edge) and no dependencies. The backend is an optional dependency of `@atlasauth/pca`, loaded lazily; if it is absent the suites are reported unsupported and verification fails closed. LESS suites are implemented by the TypeScript reference only and are not in the shared conformance corpora; the other verifiers reject them as an unknown `alg`. The wasm reproduces the 100 official known-answer tests, matches native builds byte for byte on 600+ random inputs, and passed sanitizer runs; sanitizer fuzzing also found three memory-safety defects in the unmodified upstream verifier, which the wrapper works around. It is unaudited; use the hybrid.
- SHA-384 hash agility for Merkle and canonical hashing (non-breaking).
- Optional quantum-entropy mixing for key generation.
- Groth16 Policy-VM proofs are bound to the specific action.
- Post-quantum Module-LWE (endemic) base oblivious transfer in `@atlasauth/pca-mpc`, backed by the new `@atlasauth/pca-mpc-lwe-ot-wasm`.
- Native verifiers (Go, Python, Ruby, PHP, .NET, Java, Rust, Kotlin, Swift) reach conformance parity with the TypeScript reference, with an all-languages adversarial conformance matrix.

New packages: `create-pca-app` (scaffold a working app with `npm create pca-app@latest`), `@atlasauth/pca-fndsa-wasm`, `@atlasauth/pca-mpc-lwe-ot-wasm`. All three are published for the first time in this release; `@atlasauth/pca` and `@atlasauth/pca-mpc` now depend on the wasm packages.

All packages now ship a LICENSE file (MIT), repository / homepage / bugs / keywords metadata, an `engines` field (Node >= 20), and a README.

### Fixed

- Intel TDX: the PCK certificate chain's validity period is now checked against the verification clock (expired chains were previously accepted); issuers must be CA certificates with `keyCertSign` and respected path length, leaves must not be CAs (also applied to PCS TCB / QE issuer chains); debug quoting enclaves are refused.
- Elliptic-curve public points (Intel and AMD) are extracted through the platform key-object JWK export and fail closed; the byte-scan SPKI fallback is gone.
- `allowDebug` was lost on the collateral verification path.
- Denial-of-service: parsing of limit expressions backtracked quadratically (a 1 MiB run of whitespace hung the parser); it is now length-capped and linear. `decodeSafetyCertificate` now enforces the same maximum JSON size as the other strict parsers.
- Hosted service: a connection-pool deadlock and a race in step-up approval under concurrent approvals.
- `@atlasauth/pca-pq-threshold`: the classical FROST aggregate was verified through the multi-signature share verifier, which expects role-bound share bytes, so hybrid artifacts and folded step-ups it had just produced failed verification. The aggregate is now verified as an Ed25519 signature under the trusted group key.
- `@atlasauth/pca-fndsa`: the missing-backend error now names the real backend package, `@atlasauth/pca-fndsa-wasm`.
- `create-pca-app`: scaffolded projects depend on `^0.2.0` of the PCA packages.
- Packaging: `@atlasauth/pca-invariants` declares `fast-check` as a runtime dependency (it was a dev dependency and the package failed to load once installed); `@atlasauth/pca-conformance` ships `vectors.json`, which its `exports` map already referenced.

### Security notes

- `grant_ref_bound` closes a replay-namespace bypass (see Breaking). Deployments that persist replay state keyed by `grant_ref` do not need migration, but clients must send the root capability id as `grant_ref`.
- Hardware-attestation verification now rejects debug-mode TEEs, expired or non-CA certificate chains, and quoting enclaves in debug mode by default.
- The cryptography in these packages, including the post-quantum, threshold, MPC and zero-knowledge components, has not been independently audited. Experimental packages are labelled as such in their READMEs. FN-DSA tracks a draft standard and its encodings may change before the final FIPS 206 text.
- Report vulnerabilities through the repository's security advisory channel rather than a public issue.
