# Changelog

All notable changes to the `@atlasauth/pca*` packages and `create-pca-app`. Every package in the family is versioned in lockstep, so a release bumps all of them together. While the version is 0.x, minor releases may contain breaking changes.

## 0.3.0 - 2026-10-08

Lockstep release of every package in the family (all `@atlasauth/pca*` packages, `create-pca-app`, the `atlas-pca` crate and wheel, `stark-pca`, `pca-folding-ivc`, and the seven Python framework adapters). **0.2.0 is superseded: it shipped the defects listed below, several of them security-relevant. Upgrade to 0.3.0.** The affected packages are called out per entry.

### Breaking

- **`@atlasauth/pca-scitt`: the Merkle leaf format changed.** Leaves are now `SHA-256(0x00 || statement bytes)` per RFC 9162, and receipts carry a detached payload (RFC 9942 section 4.4). Logs and receipts produced by 0.2.0 do not verify under 0.3.0. Migration: re-issue receipts from a log rebuilt with 0.3.0; keep 0.2.0 only to read historical receipts.
- **`stark-pca` (crate) and `stark-pca-plonky3`: the opaque `policy_commitment` and `action_commitment` are now bound in full (256 bits), which changes the public-input layout** (`stark-pca`: 16 to 24 field elements; Plonky3: 16 to 30). Proofs generated by 0.2.0 do not verify. Both commitments must now be exactly 64 hex digits; anything else is refused instead of truncated. Migration: regenerate proofs with 0.3.0 and make sure callers pass 64-hex-digit SHA-256 commitments. The verifier also now pins the exact proof options and trace shape, so proofs made with non-default options are rejected.
- **`@atlasauth/pca-vdf`: `setup` is renamed `insecureDevSetup`** (its result is branded `insecureDevOnly`). The timelock functions refuse its moduli, any modulus under 2048 bits and structurally weak moduli unless `allowInsecureDevModulus: true` is passed. Migration: use a production modulus from a trusted setup for real timelocks; rename calls to `insecureDevSetup` in tests and demos.
- **`@atlasauth/pca-bbs`: `keyGen` output changed** (see Fixed). Keys derived with `keyGen` under 0.2.0 differ from 0.3.0 and from other implementations; re-derive them from the key material or keep the stored scalars.
- **`@atlasauth/pca-dpop`, `-sdjwt`, `-vc`, `-spiffe`: stricter verification.** Proofs and credentials that relied on a missing check are now rejected (DPoP nonce/ath when the verifier supplies `expectedNonce`/`accessToken`; SD-JWT key-binding JWTs without `iat`/`aud`; VC and SVID algorithm pinning; X509-SVID leaf rules). See Fixed for each.
- **`@atlasauth/pca-ap2`: x402 settlement fields changed** to match the x402 v1 specification (`maxAmountRequired` in atomic units, standard base64 `X-PAYMENT`). Counterparties that parsed the 0.2.0 shape need updating.

### Fixed

- **Security: `@atlasauth/pca-vdf` `vdfVerify` / `verifyTimelock` accepted `y = 0, pi = 0` for any input**, releasing a timelock with no work.
- **Security: `@atlasauth/pca-mpc-wasm` accepted non-canonical Ed25519 point encodings** (`y >= p`; `x = 0` with the sign bit set).
- **Security: `@atlasauth/pca-oprf` accepted non-canonical scalars** (`s` and `s + L` both verified).
- **Security: `stark-pca` / `stark-pca-plonky3` bound only a 64 to 128 bit prefix of the opaque commitments** (see Breaking), and `stark-pca` panicked or aborted on malformed or corrupted proofs (now bounded, fail-closed decoding via `proof_from_bytes` / `verify_release_bytes`).
- **Security: `@atlasauth/pca-ciba` `auth_req_id` was guessable** (derived from public fields); it is now 160 random bits, and a repeated start no longer resets an approved decision.
- **Security: `@atlasauth/pca-gateway` Envoy ext_authz adapter denied every request with a query string.**
- **`@atlasauth/pca-scitt`**: RFC 9162 leaf format (see Breaking), plus CBOR codec fixes.
- **`@atlasauth/pca-bbs`**: `keyGen` used the wrong domain tag.
- **`@atlasauth/pca-fhe`**: crash on all-zero policy weights and a roughly 80 MB WASM memory leak per call on malformed blobs.
- **`@atlasauth/pca-sdjwt`, `-dpop`, `-vc`, `-spiffe`, `-webbotauth`, `-attest-eat`**: standards-conformance fixes listed in the sections below.
- **The seven Python adapters (LangGraph, CrewAI, Google ADK, Haystack, Microsoft Agent Framework, FastMCP, Pydantic AI) now work with the real, pinned framework releases**; 0.2.0 tool wrappers could not be built or lost settings against current releases, the Agent Framework middleware never allowed a call, and ADK session-state proofs were not delivered. They require `atlas-pca>=0.3.0,<0.4`.
- Validation added across the family: official vectors and independent-implementation cross-checks (details below).

### Upgrade notes

1. Bump every `@atlasauth/pca*` dependency to `^0.3.0` together; the family is versioned in lockstep and mixing 0.2.x with 0.3.x is not supported.
2. Python: `pip install -U atlas-pca` and any adapter; adapters now pin `atlas-pca>=0.3.0,<0.4`.
3. Rust: `atlas-pca`, `stark-pca` and `pca-folding-ivc` 0.3.0. Regenerate any `stark-pca` proofs.
4. Re-issue SCITT receipts and re-derive BBS keys as described above.

### Details

#### Adapter end-to-end tests

- The Python agent-framework adapters (LangGraph, CrewAI, Google ADK, Haystack, Microsoft Agent Framework, FastMCP, Pydantic AI) now ship end-to-end tests that run against the real, pinned framework (`make test-real` in each package). They found and fixed integration bugs: the LangGraph, CrewAI, Agent Framework and Haystack tool wrappers could not be built or lost settings against current framework releases, the Agent Framework middleware never allowed a call, and ADK session-state proofs were not delivered to tools that did not declare a context parameter.

#### Zero-knowledge crate validation

- `stark-pca`: fixed verifier panics on malformed proofs and an allocation abort on corrupted length prefixes (new `proof_from_bytes` / `verify_release_bytes`; exact option and trace-shape checks). Added per-section mutation tests, per-field public-input tampering tests and a cross-check against the TypeScript reference risk model.
- `pca-folding-ivc`: added tests on the committed proof, wrong public IO, over-budget and out-of-range rejection with asserted reasons, and byte-flip rejection.


#### Standards validation: OPRF, BBS, BLS aggregation, Ed25519 curve core

- `@atlasauth/pca-bbs`: **fixed `keyGen` to use the draft's key-generation domain tag** (`api_id || "KEYGEN_DST_"`). The previous tag omitted the `H2G_HM2S_` part of the api id, so keys derived from the same key material did not match other implementations. Secret keys derived with `keyGen` from earlier versions differ and must be re-derived or kept as stored scalars. Validated against the full official draft fixture set (key generation, generators, signatures, proofs, hash-to-scalar) and against the independent `zkryptium` crate in both directions. Added `verifyDetailed` and `proofVerifyDetailed`, which report why a verification failed.
- `@atlasauth/pca-oprf`: **scalar deserialization now rejects values at or above the group order** (RFC 9497 section 4.1); previously a DLEQ proof scalar `s` and `s + L` were both accepted. Validated against all RFC 9497 ristretto255-SHA512 test vectors (OPRF, VOPRF, POPRF) and the independent Rust `voprf` crate in both directions.
- `@atlasauth/pca-aggsig`: validated against the 90 BLS12-381 reference vectors of `ethereum/bls12-381-tests` (the draft itself has no vectors) and against `py_ecc` in both directions; rogue-key and proof-of-possession negatives added. No code changes.
- `@atlasauth/pca-mpc-wasm`: **the curve core now rejects non-canonical point encodings** (`y >= p`, and `x = 0` with the sign bit set), as RFC 8032 section 5.1.3 requires; the previous build accepted both. Found by the Wycheproof Ed25519 suite (case 151). Validated against the RFC 8032 vectors and all 151 Wycheproof cases from both TypeScript and new Rust `#[test]`s. The `.wasm` artifact was rebuilt (new SHA-256 in the README).

#### Gateway, CIBA, AP2/x402 and EAT standards validation

- `@atlasauth/pca-gateway`: **fixed the Envoy ext_authz adapter denying every request that has a query string** (Envoy forwards the request target including `?query`, and route matching used it verbatim, so `/refunds?x=1` was an unmapped route). Added tests against the real Fetch `Request`/`Response` classes, the Worker entry running in `workerd` (Miniflare), the AWS-documented Lambda authorizer events (REST, HTTP API 1.0 and 2.0) and the Envoy ext_authz request shape (constructed, Envoy not run).
- `@atlasauth/pca-ciba`: **`auth_req_id` was derived from public step-up fields and was therefore guessable** (CIBA Core 7.3 requires at least 128 bits of entropy); the broker now issues 160 random bits. **Starting a flow twice for one step-up silently reset an approved decision to pending**; a repeated start now returns the live flow. `requested_expiry` must be a positive integer, the verb is rejected if it cannot be a single scope-token (a space used to smuggle extra scopes), and `binding_message` is sanitized to one short plain-text line. Validated with the CIBA Core 1.0 examples and the `openid-client` library end to end.
- `@atlasauth/pca-ap2`: checked against the official AP2 schemas and documentation examples (Ajv). **The mandate chain is not the SD-JWT format the current AP2 schemas define**; the README and package description no longer claim wire compatibility. x402 settlement fixed against the x402 v1 specification: `maxAmountRequired` is now in atomic units (it was the decimal amount), `X-PAYMENT` is standard base64 (it was base64url), and `error` and `maxTimeoutSeconds` are present.
- `@atlasauth/pca-attest-eat`: tests only. RFC 7515 A.3, RFC 8037 A.4, RFC 7519 6.1 and RFC 9711 Appendix A examples, plus two-way checks against `jose`. Limits found are recorded in the README (full `application/eat+jwt` typ refused; lenient base64url in the signature segment).

#### FHE risk gate and VDF timelock validation

- `@atlasauth/pca-vdf`: **fixed `vdfVerify` / `verifyTimelock` accepting `y = 0, pi = 0` (or any multiple of the modulus) for every input and step count**, which released a timelock with zero work. `y`, `pi` and `x` must now be canonical units of the group; `vdfVerifyDetailed` reports the refusal reason. **Breaking:** `setup` is renamed `insecureDevSetup` (result branded `insecureDevOnly`), and the timelock functions refuse its moduli, anything under 2048 bits and structurally weak moduli unless `allowInsecureDevModulus: true` is passed (`checkProductionModulus`). The bundled RSA-2048 modulus is now compared with the RSA Laboratories and Wikipedia published digits; prover and verifier are cross-checked with an independent Python/GMP implementation (self-written vectors, labelled as such).
- `@atlasauth/pca-fhe`: **fixed evaluation crashing on a policy whose scaled weights or kappa-weights are all zero**, and **fixed a WASM memory leak (about 80 MB per call) on malformed or truncated blobs**; blobs are now validated against the SEAL stream envelope first and all SEAL objects are released on every path. Added property-based tests against the plaintext risk gate, a two-way cross-check against TenSEAL 0.3.18 (independent SEAL build), a parameter-security assertion against the HE Standard 128-bit table, and reason-asserting tamper and wrong-key negatives.

#### Identity and transparency standards validation

- `@atlasauth/pca-scitt`: **the Merkle leaf was canonical JSON of the base64url statement, so no off-the-shelf RFC 9162 verifier could check a receipt**; leaves are now `SHA-256(0x00 || statement bytes)` and receipts carry a detached payload (RFC 9942 section 4.4). Logs and receipts from earlier builds do not verify. Added `checkStatement` (returns the failure reason), RFC 9162 consistency proofs (`TransparencyService.consistencyProof`, `verifyConsistencyProof`), and fixes to the CBOR codec (a leading U+FEFF in text was silently dropped; negative integers below -(2^53-1) were accepted; floats were reported as "non-minimal integer"). Validated with the 82 RFC 8949 Appendix A vectors, `cose-wg/Examples`, the Certificate Transparency 8-leaf tree and 196 `transparency-dev/merkle` probes, and two-way checks with pycose, cbor2 and pymerkle.
- `@atlasauth/pca-sdjwt`: **the verifier only understood flat, top-level disclosures and `present()` threw on any array-element disclosure**, so none of the SD-JWT examples in RFC 9901 could be processed. Verification now follows RFC 9901 section 7.1 (recursive `_sd` and `...`, decoys, reused digests, unreferenced and colliding disclosures, security-critical claims, default `_sd_alg`), requires a KB-JWT `iat` and `aud`, and adds `expectedKbAudience` and `kbMaxAgeSec`. All eight SD-JWTs in RFC 9901 verify under its published key; credentials and presentations interoperate with `@sd-jwt/core` 0.22.0 in both directions.
- `@atlasauth/pca-dpop`: **`verifyDpopProof` ignored `nonce` and `ath`** (they were documented but never enforced). Added `expectedNonce` and `accessToken`. The three RFC 9449 example proofs verify (and match an independent `node:crypto` signature check); PyJWT 2.10.1 interoperates in both directions.
- `@atlasauth/pca-vc`: **`_sd_alg` was emitted inside `credentialSubject` (RFC 9901 requires the top level), which `@sd-jwt/core` rejects**, and **`verifyPassportVC` did not pin the algorithm, so a raw public key could be used as an HMAC secret**. Also checks `typ`, the VC 2.0 context and type, duplicate and unexpected disclosures. `verifyRequestSignature` gained `requiredComponents`, `maxAgeSec` and an `alg` check. did:key base58btc is validated against the multiformats vectors and Python `multiformats`/`base58` (43 keys); RFC 9421 signatures interoperate with `http-message-signatures` 2.0.1.
- `@atlasauth/pca-spiffe`: **`parseX509Svid` accepted any certificate with one URI SAN, including CA certificates and certificates without `digitalSignature`**, and **`verifyJwtSvid` accepted HS256 when given raw key bytes**. Added the X509-SVID leaf rules, `verifyX509Svid` (chain, CA flags, `keyCertSign`, path length, validity, trust domain), DER-based SAN extraction and the JWT-SVID algorithm and `typ` rules. Validated with go-spiffe's character rules and X.509-SVID test certificates, py-spiffe 0.3.2, and OpenSSL and Python `cryptography` chain verdicts.
- `@atlasauth/pca-webbotauth`: added the dictionary form of `Signature-Agent` (`"signature-agent";key="..."`, as in the current draft and Cloudflare's library), `components`, and `requireExpires`; parameters are emitted in the draft's order. The draft-05 Ed25519 vectors for no `Signature-Agent` and the legacy string form are reproduced byte for byte, and RFC 9421 B.2.6 verifies. **The draft-05 vector A.2.2 is signed over the unquoted dictionary member value, contradicting RFC 9421 section 2.1.2 and its own printed signature base**; this package and `web-bot-auth` 0.2.0 reject it, and the test documents the discrepancy.
- `stark-pca` and `stark-pca-plonky3` (security): **the opaque `policy_commitment` and `action_commitment` were bound into the proof by a prefix only (128 bits in `stark-pca`, 64 bits in the Plonky3 crate)**, so a SHA-256 commitment had at best 64-bit / 32-bit collision / second-preimage strength. Both must now be exactly 64 hex digits (anything else is refused) and are bound in full: four 64-bit limbs per commitment in `stark-pca` (public inputs 16 to 24 elements), eight 32-bit limbs per commitment in the Plonky3 crate (Goldilocks is below 2^64; public values 16 to 30). Committed proof fixtures regenerated; tests flip every limb, and a regression test covers commitments differing only in the last hex digit. This is a public-input layout change: old proofs do not verify.
- `@atlasauth/pca-attest-eat`: `verifyEAT` accepts the short `typ` form `eat+jwt` as equivalent to `application/eat+jwt` (RFC 7515 4.1.9, case-insensitive); other `typ` values are still refused.
- Validation (post-quantum): `@atlasauth/pca-pq-threshold` ML-DSA-65 is tested against the official NIST ACVP FIPS 204 vectors and against dilithium-py and liboqs; `@atlasauth/pca-mpc-lwe-ot-wasm` against the official ACVP FIPS 203 ML-KEM-768 vectors and kyber-py; `@atlasauth/pca-fndsa-wasm` against an independent C implementation in both directions (no official FN-DSA vectors exist yet); `@atlasauth/pca-fndsa` integration tests now run through the real wasm backend. Note: the K-PKE key derivation in `@atlasauth/pca-mpc-lwe-ot-wasm` differs from ML-KEM key generation and is documented as such.

## 0.2.0 - 2026-10-08

> Superseded by 0.3.0. 0.2.0 shipped the defects listed under 0.3.0 Fixed (including security fixes in pca-vdf, pca-mpc-wasm, pca-oprf and the STARK crates); upgrade.

### Breaking

- **The resource-server verifier now lives in `@atlasauth/pca`.** Verdict computation and the framework-neutral `requirePCA` guard are exported from `@atlasauth/pca` itself. PCA no longer depends on any other product's SDK. The framework middleware packages (`@atlasauth/pca-fetch`, `-express`, `-fastify`, `-hono`, `-next`) depend only on `@atlasauth/pca` and no longer depend on any other product's SDK.
- **A new mandatory verification check, `grant_ref_bound`.** The holder-signed `grant_ref` of a PCActn must be a non-empty string byte-equal to the id of the root capability (`cap_chain[0].id`). The check is part of the default required checks and of the discovery defaults, and it fails closed on an empty or malformed chain. Previously a holder could sign arbitrary fresh `grant_ref` values and land on an empty replay/budget namespace for each action. PCActns that do not carry a matching `grant_ref` are now rejected; the conformance vectors were extended accordingly (the check is implemented identically in the TypeScript reference and the Go, Python, Ruby, PHP, .NET, Java, Rust, Kotlin and Swift verifiers).
- **AMD SEV-SNP: the invented "weights" slot is removed.** SEV-SNP has no native weights-measurement field; the previous convention read bytes that are actually part of the AMD report's committed-TCB / build fields. Reports no longer yield a `weights_measured` claim from those bytes. Anything that relied on that claim must obtain model-weights evidence from a source that really provides it.
- **`@atlasauth/pca-attest-eat` no longer carries its own AMD chain cryptography.** `verifySevSnpSignature` and `verifyAmdCertChain` are removed; `verifyAmdAttestation` (now async, as is `verifyFreshAttestedEAT`) delegates to the hardened `verifyGenuineSevSnpReport` in `@atlasauth/pca`. It now requires the verifier clock (`nowMs`; `verifyFreshAttestedEAT` passes its `now`), a `family` (`milan`, `genoa` or `turin`) or an explicit `trustAnchorArkSpkiSha384` in place of `rootFingerprint`, rejects debug-enabled guests unless `allowDebug` is set (replacing `requireDebugDisabled`), and enforces CA roles, strict extension parsing and the VCEK-to-report binding. `KNOWN_AMD_ARK_SPKI_SHA384` is now `{ milan, genoa, turin }`, so genuine Genoa hardware (Azure SEV-SNP) verifies.
- **The synthetic attestation profiles (SEV-SNP, Intel TDX, NVIDIA CC) are removed.** Use the real-evidence verifiers listed below.
- **NVIDIA GPU root: no workload identity by default.** The GPU root no longer derives a `runtime_measurement` from GPU state, so it composes with CPU TEE roots in an N-of-M policy instead of producing a false identity conflict. The GPU measurement digest is surfaced as `hostAsserted.gpu_measurements_sha384`; standalone deployments can supply `policy.deriveIdentity`.
- **Intel TDX: debug TDs are rejected** unless the policy explicitly sets `allowDebug`.

### Added

Attestation (verified against evidence captured from real hardware and real vendor services):

- AMD SEV-SNP report verifier with per-family ARK pins (Milan, Genoa, Turin), real report-field parsing (CPUID, committed/launch TCB, firmware versions, mitigation vectors), report v5, `minCommittedTcb` / `minLaunchTcb`, and runtime-data binding checked under AMD's signature.
- Intel TDX / DCAP quote verifier (`attestIntelDcap`) including Intel PCS collateral validation (TCB info, QE identity, CRLs), MRSEAM / MRSIGNERSEAM allowlists, and runtime-data binding checked under Intel's signature.
- NVIDIA GPU confidential-computing root (`attestNvidiaSpdm`) in the real SPDM / X.509 wire format, NVIDIA RIM golden-measurement verification and CRL revocation (`attestNvidiaRim`), OCSP revocation (`attestNvidiaOcsp`), and Hopper and Blackwell support (Blackwell RIM naming, wrong-family manifest rejection).
- Azure Attestation (MAA) root covering SEV-SNP and TDX CVMs, with a `sevSnpMinTcb` minimum reported-TCB policy and surfaced SVNs; built-in release-signed MAA trust pins (no trust-on-first-use) with multi-vantage corroboration.
- GCP Confidential Space root covering SEV-SNP and TDX on GCP.
- Multi-root N-of-M attestation policy across hardware roots, plus software/HSM post-quantum and PUF / TPM EK roots.
- Signed, versioned allowlist manifests (`attestAllowlist`), a rotation-safe MAA signing-key trust store (`attestMaaKeys`), transparency-anchored allowlist rollback protection, and crash-safe durable state (`@atlasauth/pca/durable-state`).
- `@atlasauth/pca-attest-eat`: per-session attestation freshness and channel binding emitting EAT (RFC 9711).

Authorization and protocol:

- Post-quantum t-of-n quorum certificates (`pqThreshold`): a composition of independent ML-DSA / SLH-DSA signatures with assumption diversity and rotation certificates. This is a quorum of signatures, not a compact threshold signature.
- Replay-store contract (`ReplayStore` / `CounterStore`, `guardPCActnReplay`) with a reference in-memory store, so multi-server deployments can plug in a shared store.
- Runtime-data binding for hardware attestation evidence (nonce and PCA action bound into the signed evidence).
- Step-up re-attestation: a held, attested step-up whose attestation nonce lapsed can complete with a fresh single-use nonce instead of failing unusably (hosted service).
- FN-DSA (Falcon, FIPS 206 draft) registered as the `fn-dsa-512` and `fn-dsa-1024` signature suites, backed by the new `@atlasauth/pca-fndsa-wasm`.
- LESS (a code-based signature, NIST additional-signature Round 2 candidate, not a standard) registered as the opt-in `less-cat1` and `hybrid-ed25519-less-cat1` suites (category 1, 97,484-byte public key, 1,153 to 1,329-byte signatures), usable on PCActn leaves and capability hops. Backed by the new `@atlasauth/pca-less-wasm`: the official LESS reference compiled to WebAssembly with a portable loader (Node, browsers, Deno, Bun, edge) and no dependencies. The backend is an optional dependency of `@atlasauth/pca`, loaded lazily; if it is absent the suites are reported unsupported and verification fails closed. LESS suites are implemented by the TypeScript reference only and are not in the shared conformance corpora; the other verifiers reject them as an unknown `alg`. The wasm reproduces the 100 official known-answer tests, matches native builds byte for byte on 600+ random inputs, and passed sanitizer runs; sanitizer fuzzing also found three memory-safety defects in the unmodified upstream verifier, which the wrapper works around. It is unaudited; use the hybrid.
- SHA-384 hash agility for Merkle and canonical hashing (non-breaking).
- Optional quantum-entropy mixing for key generation.
- Groth16 Policy-VM proofs are bound to the specific action.
- Post-quantum Module-LWE (endemic) base oblivious transfer in `@atlasauth/pca-mpc`, backed by the new `@atlasauth/pca-mpc-lwe-ot-wasm`.
- Native verifiers (Go, Python, Ruby, PHP, .NET, Java, Rust, Kotlin, Swift) reach conformance parity with the TypeScript reference, with an all-languages adversarial conformance matrix.

New packages: `create-pca-app` (scaffold a working app with `npm create pca-app@latest`), `@atlasauth/pca-fndsa-wasm`, `@atlasauth/pca-mpc-lwe-ot-wasm`. All three are published for the first time in this release; `@atlasauth/pca` and `@atlasauth/pca-mpc` now depend on the wasm packages.

All packages now ship a LICENSE file (MIT), repository / homepage / bugs / keywords metadata, an `engines` field (Node >= 20), and a README.

### Fixed

- Intel TDX: the PCK certificate chain's validity period is now checked against the verification clock (expired chains were previously accepted); issuers must be CA certificates with `keyCertSign` and respected path length, leaves must not be CAs (also applied to PCS TCB / QE issuer chains); debug quoting enclaves are refused.
- Elliptic-curve public points (Intel and AMD) are extracted through the platform key-object JWK export and fail closed; the byte-scan SPKI fallback is gone.
- `allowDebug` was lost on the collateral verification path.
- Denial-of-service: parsing of limit expressions backtracked quadratically (a 1 MiB run of whitespace hung the parser); it is now length-capped and linear. `decodeSafetyCertificate` now enforces the same maximum JSON size as the other strict parsers.
- Hosted service: a connection-pool deadlock and a race in step-up approval under concurrent approvals.
- `@atlasauth/pca-pq-threshold`: the classical FROST aggregate was verified through the multi-signature share verifier, which expects role-bound share bytes, so hybrid artifacts and folded step-ups it had just produced failed verification. The aggregate is now verified as an Ed25519 signature under the trusted group key.
- `@atlasauth/pca-fndsa`: the missing-backend error now names the real backend package, `@atlasauth/pca-fndsa-wasm`.
- `create-pca-app`: scaffolded projects depend on `^0.2.0` of the PCA packages.
- Packaging: `@atlasauth/pca-invariants` declares `fast-check` as a runtime dependency (it was a dev dependency and the package failed to load once installed); `@atlasauth/pca-conformance` ships `vectors.json`, which its `exports` map already referenced.

### Security notes

- `grant_ref_bound` closes a replay-namespace bypass (see Breaking). Deployments that persist replay state keyed by `grant_ref` do not need migration, but clients must send the root capability id as `grant_ref`.
- Hardware-attestation verification now rejects debug-mode TEEs, expired or non-CA certificate chains, and quoting enclaves in debug mode by default.
- The cryptography in these packages, including the post-quantum, threshold, MPC and zero-knowledge components, has not been independently audited. Experimental packages are labelled as such in their READMEs. FN-DSA tracks a draft standard and its encodings may change before the final FIPS 206 text.
- Report vulnerabilities through the repository's security advisory channel rather than a public issue.

## 0.1.0

Initial public release of the PCA package family.
